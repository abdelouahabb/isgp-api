Comprendre sans confusion : Encodage vs Hachage vs Signature HMAC vs Chiffrement

          

            En sécurité des APIs et administration système Linux, confondre ces cinq opérations conduit à des failles critiques. Voici la matrice de décision exacte à conserver en permanence :
          

          

            

              
                

                  Opération
                  Est-ce Réversible ?
                  Utilise une Clé Secrète ?
                  Objectif Exact
                  Outils Standards (OpenSSL / Python)
                  Cas d'Usage en API Web
                

              
              
                

                  1. Encodage
(Base64, Hex, UTF-8)		
                  Oui, par tout le monde (0 sécurité)
                  Non
                  Transporter des octets binaires dans un canal texte (HTTP/JSON)
                  base64, openssl base64, base64.b64encode()
                  En-tête Authorization: Basic, segments d'un jeton JWT
                

                

                  2. Hachage Rapide
(SHA-256, SHA-512)		
                  Non (Irréversible)
                  Non
                  Garantir l'intégrité d'un fichier ou calculer l'empreinte d'une clé haute entropie
                  openssl dgst -sha256, sha256sum, hashlib.sha256()
                  Vérifier qu'une archive n'est pas altérée, stocker l'empreinte d'une API Key
                

                

                  3. Hachage Lent Salé (KDF)
(Scrypt, PBKDF2, Argon2)		
                  Non (Irréversible + Lent)
                  Non (Sel aléatoire public inclus)
                  Protéger les mots de passe humains contre le cassage par GPU
                  openssl passwd -6, generate_password_hash()
                  Colonne password_hash de la table users en base SQL
                

                

                  4. Signature HMAC
(HMAC-SHA256)		
                  Non (Vérifié par recalcul)
                  Oui (Clé secrète partagée)
                  Prouver à la fois l'intégrité ET l'authenticité de l'émetteur
                  openssl dgst -sha256 -hmac, hmac.new()
                  Signature des jetons Bearer/JWT (HS256) et des Webhooks (X-Webhook-Signature)
                

                

                  5. Chiffrement Symétrique
(AES-256-CBC / GCM)		
                  Oui (Avec la même clé secrète)
                  Oui (1 clé secrète unique pour chiffrer et déchiffrer)
                  Rendre un fichier ou une colonne illisible aux tiers tout en pouvant le restaurer
                  openssl enc -aes-256-cbc -pbkdf2, cryptography.fernet
                  Chiffrer une sauvegarde SQLite (.db.enc), un fichier .env ou un secret bancaire
                

                

                  6. Chiffrement Asymétrique
(RSA-4096, Ed25519)		
                  Oui / Vérifiable (Paire Privée / Publique)
                  Oui (Clé Privée secrète + Clé Publique distribuée)
                  Signer avec la clé privée et permettre à tous de vérifier avec la clé publique
                  openssl genpkey, openssl pkey, ssh-keygen
                  Certificats HTTPS/TLS, clés SSH, jetons JWT inter-microservices (RS256 / EdDSA)

Les 14 Commandes openssl Indispensables en Terminal Linux

        

          

            
              

                Besoin Opérationnel
                Commande Exacte à Exécuter sous Linux
                Explication Technique & Précautions
              

            
            
              

                1. Générer un cookie_secret
(256 bits en Hexadécimal)		
                openssl rand -hex 32
                Produit 64 caractères hexadécimaux (32 octets d'entropie pure) parfaits pour TORNADO_COOKIE_SECRET.
              

              

                2. Générer une clé aléatoire
(Format Base64)		
                openssl rand -base64 32
                Produit une chaîne aléatoire compacte idéale pour une clé d'API (X-API-Key) ou un mot de passe BDD.
              

              

                3. Hacher un texte en SHA-256
(Sans saut de ligne \n)		
                printf '%s' "mon_texte" | openssl dgst -sha256
                Toujours utiliser printf '%s' (et non echo qui ajoute un \n invisible modifiant le hash !).
              

              

                4. Hacher un fichier en SHA-256
(Contrôle d'intégrité)		
                openssl dgst -sha256 ecole_isgp.db
                Calcule l'empreinte SHA-256 d'un fichier SQLite ou d'une archive (équivalent à sha256sum).
              

              

                5. Signer en HMAC-SHA256
(Test de Webhook / JWT)		
                printf '%s' '{"id":1}' | openssl dgst -sha256 -hmac "cle_secrete"
                Calcule exactement la signature attendue dans l'en-tête X-Webhook-Signature de votre API Tornado.
              

              

                6. Encoder / Décoder en Base64
                printf '%s' "admin:pass" | openssl base64 -A
echo "YWRtaW46cGFzcw==" | openssl base64 -d		
                L'option -A garde la sortie sur une seule ligne ; -d décode le Base64 vers le texte d'origine.
              

              

                7. Chiffrer un fichier en AES-256
(Sauvegarde sécurisée)		
                openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 -in base.db -out base.db.enc
                Chiffre base.db avec AES-256, un sel aléatoire et 600 000 itérations PBKDF2 (demande un mot de passe).
              

              

                8. Déchiffrer un fichier AES-256
                openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in base.db.enc -out base.db
                L'option -d (*decrypt*) restaure le fichier original à l'octet près à partir du mot de passe.
              

              

                9. Générer une clé privée RSA 4096
                openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out private.pem
                Crée une clé privée asymétrique RSA de 4096 bits. Toujours protéger par chmod 600 private.pem.
              

              

                10. Extraire la clé publique RSA
                openssl pkey -in private.pem -pubout -out public.pem
                Extrait la clé publique public.pem qui peut être partagée sans risque avec tous les microservices.
              

              

                11. Générer une clé Ed25519
(Courbe elliptique moderne)		
                openssl genpkey -algorithm Ed25519 -out ed_priv.pem && openssl pkey -in ed_priv.pem -pubout -out ed_pub.pem
                Algorithme asymétrique moderne : clés ultra-courtes, signatures ultra-rapides et sécurité maximale.
              

              

                12. Créer un certificat HTTPS/TLS
(Auto-signé 365 jours)		
                openssl req -x509 -newkey rsa:4096 -nodes -keyout key.pem -out cert.pem -days 365 -subj "/CN=localhost"
                Génère key.pem et cert.pem pour tester HTTPS en local (ex: Nginx ou Gunicorn --certfile).
              

              

                13. Inspecter un certificat .pem
                openssl x509 -in cert.pem -noout -subject -issuer -dates -fingerprint -sha256
                Affiche le propriétaire (subject), l'autorité émettrice (issuer) et les dates d'expiration du certificat.
              

              

                14. Tester le TLS d'une API distante
                openssl s_client -connect api.domaine.dz:443 -servername api.domaine.dz </dev/null
                Se connecte en TLS au port 443 pour diagnostiquer la chaîne de certificats et la version TLS (TLS 1.2 / 1.3).

          Administration Linux & DevOps
        


        

          Lorsqu'une API est déployée sur un serveur Linux (Ubuntu, Debian, RHEL/Rocky), l'ingénieur backend utilise quotidiennement ces commandes pour diagnostiquer les ports, filtrer les réponses JSON, analyser les logs d'erreurs et sécuriser les processus :
        


        

          

            
              

                Catégorie & Action
                Commande Linux de Référence
                Utilité en Développement & Production d'API
              

            
            
              

                Réseau — Voir les ports ouverts
                sudo ss -tulpn | grep -E "8888|8001|80|443"
                Affiche tous les processus en écoute TCP/UDP avec leur numéro de processus (PID).
              

              

                Réseau — Identifier qui bloque un port
                lsof -i :8888  ou  fuser 8888/tcp
                Indispensable face à l'erreur OSError: [Errno 98] Address already in use au lancement de Tornado.
              

              

                Processus — Arrêter proprement
                kill -15 <PID>  (ou kill -9 <PID> si figé)
                -15 (SIGTERM) permet à IOLoop.current().stop() de terminer les requêtes en cours avant de s'éteindre.
              

              

                Réseau — Tester un port TCP
                nc -zv 127.0.0.1 8888
                Vérifie avec Netcat si le port TCP 8888 (ou 5432 pour PostgreSQL) est ouvert à travers le pare-feu.
              

              

                Réseau — Diagnostic DNS & IP
                dig +short api.domaine.dz  |  ip -br a
                Vérifie la résolution DNS d'un nom de domaine et liste les adresses IP des cartes réseau du serveur.
              

              

                Réseau — Capturer les paquets HTTP
                sudo tcpdump -i lo -A -s 0 'tcp port 8888'
                Capture et affiche en ASCII (-A) les trames TCP/HTTP brutes circulant sur le port 8888.
              

              

                JSON — Formater & Filtrer avec jq
                curl -s http://127.0.0.1:8888/api/sandbox/formations | jq '.data[] | {id, titre}'
                Extrait, colorise et transforme les réponses JSON directement dans un pipeline Bash.
              

              

                Logs — Surveillance temps réel
                tail -f access.log | grep --line-buffered -E " (401|403|429|500) "
                Affiche en direct uniquement les requêtes en échec ou bloquées par la sécurité.
              

              

                Logs — Top 10 des IP (Anti-DoS)
                awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10
                Compte le nombre de requêtes par adresse IP cliente dans les journaux Nginx/Apache pour repérer un abus.
              

              

                Sécurité — Verrouiller .env et clés
                chmod 600 .env private.pem
                Interdit la lecture du fichier de secrets à tout autre compte utilisateur de la machine Linux (-rw-------).
              

              

                Sécurité — Pare-feu Linux ufw
                sudo ufw allow 22/tcp && sudo ufw allow 443/tcp && sudo ufw enable
                Ferme tous les ports entrants du serveur sauf SSH (22) et HTTPS (443), rendant le port Gunicorn 8000 inaccessible de l'extérieur.

                sudo systemctl restart isgp-api && sudo journalctl -u isgp-api -f
                Redémarre les workers Gunicorn de production et affiche leurs journaux système en continu.
              

            
          

        

      


      
      

        

          
Addendum III — Référentiel des Types MIME (Content-Type / Accept) & Comment les Utiliser dans Tornado

          Types MIME & Négociation HTTP
        


        

          
Anatomie d'un Type MIME (type/sous-type; paramètre=valeur — RFC 6838 / IANA)

          

            Sur le réseau HTTP, le corps d'un message (Body) n'est qu'une suite d'octets. C'est le Type MIME (*Multipurpose Internet Mail Extensions*) qui indique au destinataire comment interpréter ces octets :
            
    
              
  • Content-Type (En-tête descriptif du corps envoyé) : Indique le format du corps actuel (ex: le client envoie Content-Type: application/json ou application/x-www-form-urlencoded dans son POST ; Tornado répond avec Content-Type: application/json; charset=UTF-8 via self.write(dict) ou text/html; charset=utf-8 via self.render(...)).
    • 
              
  • Accept (En-tête de négociation du client) : Le client indique à Tornado sous quel format il souhaite recevoir la réponse (ex: Accept: application/json pour un client mobile vs Accept: text/html pour un navigateur Web).
    • 
              
  • Content-Disposition (Comportement d'affichage vs téléchargement) : inline affiche le document (PDF, image) directement dans l'onglet du navigateur, tandis que attachment; filename="rapport.pdf" ouvre la boîte de dialogue de téléchargement.
    • 
              
  • X-Content-Type-Options: nosniff (Sécurité) : Interdit au navigateur de deviner le type d'un fichier par son contenu (*MIME Sniffing*), bloquant l'exécution de scripts malveillants déguisés en image ou en fichier texte.
    •

import csv, io, os
import tornado.escape
import tornado.web


# 1. INSPECTION DU TYPE MIME ENTRANT (POST : JSON vs Formulaire HTML vs Multipart)
class IngestionUniverselleHandler(tornado.web.RequestHandler):
    def post(self):
        ct = self.request.headers.get("Content-Type", "").split(";")[0].strip().lower()

        if ct == "application/json":
            donnees = tornado.escape.json_decode(self.request.body or b"{}")
            self.set_status(201)
            self.write({"source": "JSON", "recu": donnees})
            return

        if ct == "application/x-www-form-urlencoded":
            donnees = {k: self.get_body_argument(k) for k in self.request.body_arguments}
            self.set_status(201)
            self.write({"source": "Formulaire HTML (get_body_argument)", "recu": donnees})
            return

        if ct == "multipart/form-data":
            champ_titre = self.get_body_argument("titre", default="")
            fichiers = self.request.files.get("document", [])
            f_info = fichiers[0] if fichiers else {}
            nom_sain = os.path.basename(f_info.get("filename", "")) if f_info else None
            self.set_status(201)
            self.write({
                "source": "Multipart (body_arguments + request.files)",
                "titre": champ_titre,
                "fichier_nom": nom_sain,
                "fichier_mimetype": f_info.get("content_type"),
            })
            return

        self.set_status(415)
        self.write({"erreur": f"Type MIME '{ct}' non supporté (415 Unsupported Media Type)"})


# 2. NÉGOCIATION DE CONTENU (Header 'Accept') : Répondre en JSON, HTML ou CSV sur le même Handler !
class ExportFormationsHandler(tornado.web.RequestHandler):
    def get(self):
        formations = [
            {"id": 1, "titre": "Architecture API REST Tornado", "duree_jours": 5, "salle": "Salle A"},

        self.write({"total": len(formations), "data": formations})

              1. Pourquoi /api/v1 dure souvent 5 à 10 ans sans jamais passer en v2 ?
            
            

              Dans les grandes APIs mondiales (OpenAI /v1/chat/completions, Stripe /v1/charges, Kubernetes /apis/apps/v1), on voit presque toujours v1 parce que 90 % de la vie d'une API se fait par ajouts rétrocompatibles (Additive / Non-Breaking Changes) :
            

            
    
              
  • Loi de Postel (Tolerant Reader Pattern) : Lorsqu'on ajoute un nouveau champ "certifiant": true dans le JSON de /api/v1/formations, une application mobile codée il y a 2 ans qui lit uniquement formation.intitule ignore simplement la nouvelle clé sans planter.
    • 
              
  • Pourquoi écrire /api/v1 dès le Jour 1 alors ? C'est une assurance-vie architecturale : si vous publiez /api/formations sans /v1 dans 50 000 téléphones et qu'un jour vous devez changer le type d'un champ, vous êtes bloqué. Avec /api/v1 présent dès l'origine, vous montez /api/v2 à côté sans casser /api/v1 !
    • 
            

          


          

            
              2. Quand faut-il obligatoirement créer /api/v2 et comment déprécier /api/v1 ?
            
            

              On ne crée /api/v2 que lorsqu'une modification casse le code des clients existants (Breaking Change) : changement de type (5 devient {"valeur": 5, "unite": "jours"}), renommage/suppression de clé, ou nouveau champ requis en POST.
            

            
    
              
  • Coexistence par Tables de Routage URLSpec Tornado : Les deux ensembles de handlers get_v1_routes() et get_v2_routes() tournent simultanément dans la même tornado.web.Application.
    • 
              
  • En-têtes HTTP de Dépréciation (Norme IETF RFC 8594) : Tant que v1 est en sursis, le serveur injecte via self.set_header(...) : Deprecation: true, Sunset: Thu, 31 Dec 2026 23:59:59 GMT et Link: </api/v2/formations>; rel="successor-version".
    • 
            

          

        


        

          

            
              

                Nature du Changement
                Exemples Concrets en JSON / HTTP

                Ajout Rétrocompatible
(Non-Breaking / Additive)		
                
                  • Ajouter une clé JSON en sortie ("niveau": "Avancé")

                  • Créer une nouvelle route GET /api/v1/certificats

                  • Ajouter un filtre optionnel ?salle=Alger
                		
                Aucun impact : les clients existants ignorent les clés/routes qu'ils n'utilisent pas.
                Rester sur /api/v1 (Ne jamais créer une v2 pour un simple ajout !)
              

              

                Rupture de Contrat
(Breaking Change)		
                
                  • Renommer "intitule" en "titre"

                  • Changer "duree": 5 (int) en "duree": {"valeur": 5, "unite": "jours"}

                  • Rendre un nouveau champ obligatoire dans POST
                		
                Crash immédiat (KeyError, TypeError ou rejet 422 sur les apps mobiles en production).
                Créer un module de routes /api/v2 et maintenir /api/v1 avec en-têtes Deprecation + Sunset.
              

              

                Piège de la Racine JSON
(Liste brute vs Enveloppe)		
                
                  • Mauvais : Renvoyer une liste brute [ {...}, {...} ]

                  • Bon : Renvoyer {"meta": {"total": 42, "page": 1}, "data": [...]}
                		
                Si la racine est une liste [...], impossible d'ajouter total ou next_cursor sans casser la racine !
                Toujours utiliser une enveloppe objet {"meta": ..., "data": [...]} dès /api/v1 (et requis par self.write(dict) de Tornado !).
              

              

                Les 4 Stratégies de Versioning
(Où placer le numéro ?)		
                
                  1. URI Path : /api/v1/formations (80 % des APIs)

                  2. Header Date : X-API-Version: 2026-11-01 (Stripe)

                  3. MIME Accept : Accept: application/vnd.isgp.v2+json

                  4. Query Param : ?version=2
                		
                Le versioning dans l'URI (/api/v1/) est le plus lisible dans curl, Swagger UI et les blocs location de Nginx.
                Utiliser /api/v1/ dans l'URL pour les versions majeures, et un en-tête pour les sous-versions mineures.

Chapitre 1 — Architecture & Cycle de Vie d'une Connexion SQLite3 dans Tornado (run_in_executor + Pragmas de Production)

          Zéro Serveur Externe • Standard Library sqlite3
        

        

          Dans Tornado, le serveur repose sur une boucle d'événements mono-thread (IOLoop). Comme la bibliothèque standard sqlite3 effectue des entrées/sorties disque synchrones, une requête SQL lourde ou un verrou disque exécuté directement sur le thread principal figerait toutes les autres connexions de l'IOLoop. La bonne pratique d'ingénierie sous Tornado consiste à encapsuler la transaction SQLite dans une fonction synchrone appelée via await tornado.ioloop.IOLoop.current().run_in_executor(None, fn) :
        


        

          

            
Cycle d'Exécution d'une Requête SQLite Paramétrée

            
sequenceDiagram
    participant C as Client HTTP
    participant IO as Boucle IOLoop Tornado (Mono-Thread Non-Bloquant)
    participant TP as ThreadPoolExecutor (run_in_executor)
    participant S as Moteur C SQLite3 (Fichier .db + .db-wal)
    C->>IO: 1. Requête HTTP (async def get / post dans RequestHandler)
    IO->>TP: 2. await IOLoop.current().run_in_executor(None, _requete_sqlite)
    Note over IO: L'IOLoop reste 100% libre pour servir les autres clients !
    TP->>S: 3. sqlite3.connect() + PRAGMA journal_mode=WAL
    TP->>S: 4. with closing(conn.cursor()) as cur -> sqlite3_prepare_v2 + COMMIT
    S-->>TP: 5. fetchone() / fetchall() -> dict(row) + conn.close() dans finally
    TP-->>IO: 6. Résolution du Future asynchrone
    IO-->>C: 7. self.write(json) (HTTP 200 / 201)

          

          

            

              Patron d'implémentation recommandé (TORNADO) :
              
            

            
from contextlib import closing
import sqlite3
import tornado.ioloop
import tornado.web

DB_PATH = "isgp_catalogue.db"

def ouvrir_connexion_sqlite() -> sqlite3.Connection:
    conn = sqlite3.connect(DB_PATH, timeout=5.0, check_same_thread=False)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode = WAL;")   # Lectures et écritures concurrentes
    conn.execute("PRAGMA synchronous = NORMAL;") # Optimal avec WAL
    conn.execute("PRAGMA foreign_keys = ON;")    # Clés étrangères activées
    conn.execute("PRAGMA busy_timeout = 5000;")  # Attente max 5000 ms sur verrou
    return conn

class FormationsHandler(tornado.web.RequestHandler):
    async def get(self):
        salle = self.get_query_argument("salle", default="Salle A")
        def _select_sync():
            conn = ouvrir_connexion_sqlite()
            try:
                with closing(conn.cursor()) as cur:
                    cur.execute("SELECT * FROM formations WHERE salle = ?", (salle,))
                    return [dict(r) for r in cur.fetchall()]
            finally:
                conn.close()
        data = await tornado.ioloop.IOLoop.current().run_in_executor(None, _select_sync)
        self.write({"data": data})

          

        


        
    
          
  • 1. Protection de l'IOLoop via run_in_executor : En déléguant l'appel sqlite3 au ThreadPoolExecutor standard via await IOLoop.current().run_in_executor(None, ...), la boucle d'événements Tornado continue d'accepter les requêtes HTTP concurrentes pendant l'accès disque.
    • 

  • 2. Connexion courte fermée dans finally : Contrairement à un serveur TCP distant, l'ouverture d'un descripteur sur un fichier SQLite local prend moins de 0.05 ms. Ouvrir et fermer proprement dans try / finally à chaque tâche garantit zéro conflit entre threads.
    • 

  • 3. Mode PRAGMA journal_mode = WAL + busy_timeout = 5000 : Permet aux threads du ThreadPoolExecutor d'exécuter des SELECT en parallèle pendant qu'un INSERT ou UPDATE est en cours.
    • 

  • 4. Activation obligatoire de PRAGMA foreign_keys = ON : SQLite désactive les clés étrangères par défaut sur chaque nouvelle connexion ; il faut toujours l'activer dans ouvrir_connexion_sqlite().

Chapitre 3 — Transactions ACID, isolation_level, Mode autocommit (Python 3.12+) & Verrous BEGIN IMMEDIATE

          Contrôle Transactionnel
        


        

          La gestion des transactions dans le module standard sqlite3 possède une particularité historique essentielle à connaître pour éviter deux pièges classiques en production : les écritures non sauvegardées (oubli de commit) et les erreurs sqlite3.OperationalError: database is locked lors de montées de verrous concurrentes.
        


        

          

            
              

                Mode Transactionnel sqlite3
                Configuration à l'ouverture
                Comportement Exact & Cas d'Usage
              

            
            
              

                1. Mode Historique par Défaut
(LEGACY_TRANSACTION_CONTROL)		
                sqlite3.connect("app.db")
(isolation_level = "" par défaut)		
                
                  Python analyse vos chaînes SQL et émet implicitement un BEGIN uniquement avant une instruction DML (INSERT, UPDATE, DELETE, REPLACE). Si vous n'appelez pas conn.commit() (ou n'utilisez pas le bloc with conn:) avant conn.close(), toutes vos modifications sont annulées silencieusement (ROLLBACK) !
                
              

              

                2. Mode Autocommit Natif SQLite
(Chaque requête s'engage seule)		
                
                  Python 3.12+ : sqlite3.connect("app.db", autocommit=True)

                  Python ≤ 3.11 : sqlite3.connect("app.db", isolation_level=None)
                		
                
                  Désactive les transactions implicites de Python : le moteur C SQLite fonctionne dans son mode natif où chaque instruction individuelle est validée immédiatement sur disque, sauf si vous démarrez explicitement un bloc cur.execute("BEGIN IMMEDIATE") ... cur.execute("COMMIT"). Très apprécié dans les frameworks asynchrones et pour piloter manuellement les verrous.
                
              

              

                3. Mode PEP 249 Strict (Python 3.12+)
(Transaction toujours ouverte)		
                sqlite3.connect("app.db", autocommit=False)
                
                  Conforme à 100% à la norme PEP 249 (comme psycopg sur PostgreSQL) : une transaction est toujours active dès la première requête (même un SELECT), et vous validez par conn.commit() ou annulez par conn.rollback().
                
              

            
          

        


        

          

            

              Attention : que fait réellement with conn: sur un objet sqlite3.Connection ?
            

            

              Contrairement à un fichier (with open(...)), utiliser with conn: sur une connexion SQLite NE FERME PAS la connexion ! Il agit uniquement comme un gestionnaire de transaction :
            

            
conn = sqlite3.connect("app.db")
try:
    with conn:
        # Si tout réussit ici -> conn.commit() est appelé automatiquement
        # Si une exception survient -> conn.rollback() est appelé automatiquement !
        conn.execute("INSERT INTO formations (titre) VALUES (?)", ("API REST",))
finally:
    conn.close()  # La fermeture du fichier .db doit toujours être appelée explicitement !

          


          

            

              Astuce Senior : Pourquoi utiliser BEGIN IMMEDIATE pour les transactions Lecture-puis-Écriture ?
            

            

              Par défaut, une transaction SQLite démarre en mode DEFERRED (elle ne prend qu'un verrou de lecture au premier SELECT). Si deux requêtes HTTP lisent le solde d'un compte en même temps puis tentent toutes deux un UPDATE, la seconde échoue immédiatement avec SQLITE_BUSY sans même attendre le busy_timeout ! En démarrant par BEGIN IMMEDIATE, SQLite réserve le droit d'écriture dès le début en respectant le busy_timeout :
            

            
conn = sqlite3.connect("app.db", isolation_level=None, timeout=5.0)
conn.execute("BEGIN IMMEDIATE")  # Réserve le verrou d'écriture proprement (attend jusqu'à 5s)
try:
    places = conn.execute("SELECT places_restantes FROM sessions WHERE id = ?", (1,)).fetchone()[0]
    if places > 0:
        conn.execute("UPDATE sessions SET places_restantes = places_restantes - 1 WHERE id = ?", (1,))
    conn.execute("COMMIT")
except Exception:
    conn.execute("ROLLBACK")
    raise

          

        

      


      
      

        

          
Chapitre 4 — Cycle de Vie du Cursor vs Connection : Faut-il fermer le Curseur (cur.close()) ? Est-ce une bonne ou mauvaise habitude ?

          Hygiène des Ressources & C-API
        


        

          C'est l'une des questions les plus fréquentes en revue de code Python : « Puisque sqlite3 permet d'écrire directement conn.execute(...) et que je ferme la connexion à la fin de la requête HTTP, dois-je quand même créer et fermer mes curseurs avec cur.close() ? »
        


        

          

            

              Verdict Ingénieur : Fermer explicitement le curseur est une EXCELLENTE habitude (4 raisons techniques)
            

            
    
              
  1. 
                Libération déterministe du verrou C (sqlite3_finalize) : Sous le capot, chaque sqlite3.Cursor maintient une machine virtuelle C compilée (sqlite3_stmt*). Si vous exécutez un SELECT et ne lisez que la 1re ligne (fetchone()) sans fermer le curseur, l'instruction reste dans l'état active statement et garde un verrou de lecture jusqu'au passage du Garbage Collector.
              
    2. 
              
  2. 
                Indépendance vis-à-vis du Garbage Collector : En CPython, le comptage de références libère souvent le curseur rapidement, mais dès qu'une trace d'exception (traceback) capture les variables locales ou que le code tourne sous PyPy, le curseur reste ouvert en mémoire si cur.close() n'est pas appelé.
              
    3. 
              
  3. 
                Portabilité directe vers PostgreSQL (psycopg) et MySQL (PyMySQL) : La méthode raccourcie conn.execute() de sqlite3 est une extension non-standard (absente de psycopg2 et PyMySQL). Sur PostgreSQL/MySQL avec un Pool de connexions, la connexion n'est jamais fermée entre deux requêtes HTTP : seul le curseur est fermé !
              
    4. 
              
  4. 
                Clarté du périmètre d'exécution : Délimiter la durée de vie du curseur indique exactement à quel moment la lecture des résultats SQL est terminée.
              
    5. 
            

          


          

            

              Attention au piège syntaxique en sqlite3 : Utilisez contextlib.closing(conn.cursor()) !
            

            

              Contrairement à psycopg (PostgreSQL) ou PyMySQL, l'objet sqlite3.Cursor de la bibliothèque standard n'implémente pas les méthodes __enter__ et __exit__ ! Écrire with conn.cursor() as cur: en sqlite3 lève une AttributeError: __enter__. Le patron canonique en Python consiste à utiliser from contextlib import closing :
            

            
from contextlib import closing

# MAUVAISE PRATIQUE (lève AttributeError en sqlite3 standard) :
# with conn.cursor() as cur:  --> AttributeError: __enter__ !

# BONNE PRATIQUE UNIVERSELLE (fonctionne en sqlite3, psycopg, PyMySQL) :
with closing(conn.cursor()) as cur:
    cur.execute("SELECT id, titre FROM formations WHERE salle = ?", ("Salle A",))
    row = cur.fetchone()
# Ici, cur.close() a été appelé automatiquement et déterministement,
# même si vous n'avez lu qu'une seule ligne sur 10 000 ou si une exception est levée !

  3. Ferme immédiatement le curseur et retourne une instance de classe Python.

def get_formation(id: int):

    • 
              
  • Sur SQLite local : aiosqlite ou run_in_executor retournant des dictionnaires purs.
    •

Chapitre 6 — sqlite3 (Bibliothèque Standard) vs APSW (Another Python SQLite Wrapper) vs aiosqlite : Quelle Différence ?

          Comparatif des Pilotes SQLite
        


        

          Lorsqu'un architecte Python conçoit un service appuyé sur SQLite, deux grandes bibliothèques C s'affrontent : le module intégré sqlite3 (dérivé de pysqlite) et APSW (Another Python SQLite Wrapper). Bien qu'elles parlent toutes deux au même moteur C SQLite, leur philosophie est radicalement opposée :
        


        

          

            
              

                Critère Technique
                sqlite3 (Standard Library Python)
                apsw (Another Python SQLite Wrapper)
                aiosqlite (Asyncio Bridge)
              

            
            
              

                Philosophie & Norme
                Implémente la norme PEP 249 (DB-API 2.0) pour offrir la même interface générique que PostgreSQL ou MySQL.
                Ne suit volontairement PAS la PEP 249 ! Expose 100% de l'API C native de SQLite (sqlite3.h) sans couche d'abstraction trompeuse.
                Enveloppe le module standard sqlite3 dans un thread d'arrière-plan piloté par des coroutines async / await.
              

              

                Installation
                Inclus d'office dans Python (zéro dépendance externe).
                Paquet C externe (pip install apsw), compilé avec la toute dernière version officielle d'amalgamation SQLite.
                Paquet externe pur Python (pip install aiosqlite).
              

              

                Gestion des Transactions
                Ouvre des transactions implicites (BEGIN caché avant INSERT/UPDATE) sauf si isolation_level=None ou autocommit=True.
                100% fidèle à SQLite C : aucune transaction cachée. Vous utilisez with connection: (qui gère même les transactions imbriquées via SAVEPOINT !) ou vos propres BEGIN IMMEDIATE.
                Hérite du comportement de sqlite3 (nécessite await db.commit()).
              

              

                Exécution de plusieurs requêtes dans un seul execute()
                Interdit : cur.execute("SELECT 1; SELECT 2;") lève ProgrammingError: You can only execute one statement at a time (et executescript() refuse les paramètres ?).
                Supporté nativement avec paramètres liés : cursor.execute("INSERT INTO a VALUES (?); SELECT * FROM a WHERE x = ?;", (10, 10)) compile et exécute chaque instruction à la suite en toute sécurité !
                Identique à sqlite3 (1 seule instruction par execute).
              

              

                Fonctionnalités Avancées SQLite C
                Sous-ensemble limité (fonctions scalaires, agrégats simples, sauvegarde backup()).
                Couverture intégrale : Tables Virtuelles (Virtual Tables), systèmes de fichiers virtuels (VFS en RAM ou chiffrés), flux Blob incrémental (zeroblob), hooks wal_hook, cache automatique de requêtes préparées, ExecutionTrace.
                Sous-ensemble de sqlite3.
              

              

                Quand le choisir ?
                Choix par défaut (95% des projets) : APIs Web, laboratoires sans installation, compatibilité SQLAlchemy et portabilité vers PostgreSQL/MySQL.

                Routes async def sous FastAPI ou Tornado si vous ne souhaitez pas utiliser de ThreadPool.

with conn:

Chapitre 8 — Sécurité SQL & Portabilité : Pourquoi ? dans SQLite vs %s dans PostgreSQL / MySQL (Norme PEP 249 / DB-API 2.0)

          Architecture & Sécurité Multi-SGBD
        


        

          En Python, tous les pilotes relationnels (sqlite3, psycopg pour PostgreSQL, PyMySQL / mysql-connector pour MySQL, oracledb, pyodbc) respectent la spécification officielle PEP 249 (Python Database API Specification v2.0). Le principe fondamental de sécurité est identique partout : séparer la compilation syntaxique de la requête (le code SQL) de la transmission des données (les paramètres). En revanche, la syntaxe du marqueur de paramètre (paramstyle) change selon le moteur de base de données :
        


        

          

            
              

                Moteur SGBD & Pilote Python
                Style PEP 249 (paramstyle)
                Syntaxe Positionnelle (Tuple en 2e argument)
                Syntaxe Nommée (Dictionnaire en 2e argument)
              

            
            
              

                SQLite 3
sqlite3 (Inclus dans Python, utilisé dans ce laboratoire)		
                qmark (?) &
named (:nom)		
                
                  cur.execute("SELECT * FROM formations WHERE salle = ? AND duree_jours >= ?", (salle, min_j))

                  Piège d'1 seul paramètre : écrire (id,) avec une virgule finale, jamais (id) !
                		
                
                  cur.execute("SELECT * FROM formations WHERE salle = :salle AND duree_jours >= :min_j", {"salle": salle, "min_j": min_j})

                  Idéal dès que la requête comporte plus de 3 paramètres.
                		
              

              

                PostgreSQL
psycopg2 / psycopg 3		
                format (%s) &
pyformat (%(nom)s)		
                
                  cur.execute("SELECT * FROM formations WHERE salle = %s AND duree_jours >= %s", (salle, min_j))

                  Utilise %s quel que soit le type (int, str, date, bool).
                		
                
                  cur.execute("SELECT * FROM formations WHERE salle = %(salle)s", {"salle": salle})
                
              

              

                MySQL / MariaDB
PyMySQL / mysql-connector		
                format (%s) &
pyformat (%(nom)s)		
                
                  cur.execute("SELECT * FROM formations WHERE salle = %s AND duree_jours >= %s", (salle, min_j))
                
                
                  cur.execute("SELECT * FROM formations WHERE salle = %(salle)s", {"salle": salle})
                
              

              

                Oracle Database
oracledb		
                named (:nom) / numeric (:1)
                cur.execute("SELECT * FROM formations WHERE salle = :1", [salle])
                cur.execute("SELECT * FROM formations WHERE salle = :salle", {"salle": salle})
              

              

                Microsoft SQL Server
pyodbc		
                qmark (?)
                cur.execute("SELECT * FROM formations WHERE salle = ?", (salle,))
                (Non supporté nativement par ODBC ; utiliser ? ou SQLAlchemy)
              

            
          

        


        

          

            

              Piège Critique sur PostgreSQL / MySQL : Ne JAMAIS confondre la virgule , et l'opérateur Python % !
            

            

              Sur MySQL et PostgreSQL, le marqueur s'écrit %s. De nombreux développeurs débutants commettent l'erreur mortelle d'utiliser l'opérateur de formatage Python % au lieu de passer un second argument à execute() :
            

            
# VULNÉRABILITÉ CRITIQUE D'INJECTION SQL (Opérateur % de Python) :
cur.execute("SELECT * FROM users WHERE email = '%s'" % email)  # INTERDIT !

# SÉCURISÉ (Virgule : le tuple est passé en 2e argument au pilote) :
cur.execute("SELECT * FROM users WHERE email = %s", (email,))  # CORRECT (PostgreSQL/MySQL)
cur.execute("SELECT * FROM users WHERE email = ?", (email,))   # CORRECT (SQLite)

          


          

            

              Ce que ni ? ni %s ne peuvent paramétrer : Les Identifiants SQL (ORDER BY, Colonnes, Tables)
            

            

              Un marqueur de requête préparée (? ou %s) ne peut lier qu'une valeur littérale. Si vous écrivez ORDER BY ?, SQLite trie sur une constante texte et non sur la colonne ! Pour dynamiser un tri ou un nom de colonne, utilisez obligatoirement une Liste Blanche (Allowlist) :
            

            
# Liste blanche stricte côté serveur (valable sur SQLite, PostgreSQL et MySQL) :
COLONNES_AUTORISEES = {"id": "id", "duree": "duree_jours", "titre": "titre"}
colonne_sure = COLONNES_AUTORISEES.get(param_utilisateur, "id")
direction_sure = "DESC" if ordre_utilisateur == "desc" else "ASC"

# Seuls les identifiants validés par dictionnaire sont interpolés ; les valeurs restent en `?` :
sql = f"SELECT * FROM formations WHERE salle = ? ORDER BY {colonne_sure} {direction_sure}"
cur.execute(sql, (salle,))

          

        


        

          Quelle stratégie adopter pour développer avec SQLite en Laboratoire puis déployer sur PostgreSQL ou MySQL en Production ?
        

        

          

            
              

                Stratégie Architecturale
                Principe de Mise en Œuvre
                Quand l'adopter ?
              

            
            
              

                Stratégie 1 — Pattern Repository (Couche d'Accès aux Données isolée)
                Interdire toute requête SQL directement dans les routes HTTP (Flask, FastAPI, Tornado). Regrouper toutes les requêtes (find_one, find_many, insert) dans une classe FormationRepository. Les routes appellent uniquement repo.find_one(1).
                Projets utilisant du SQL natif haute performance : le jour où vous passez de SQLite (?) à PostgreSQL (%s), seul le fichier repository.py est adapté, aucune route API ne change.
              

              

                Stratégie 2 — SQLAlchemy Core (text(":nom")) ou ORM
                Écrire des marqueurs nommés universels :nom via sqlalchemy.text("SELECT * FROM formations WHERE salle = :salle"). SQLAlchemy les compile automatiquement en ? pour SQLite et en %s / $1 pour PostgreSQL et MySQL selon la variable d'environnement DATABASE_URL.
                Applications d'entreprise devant tourner sur sqlite:///lab.db en développement local / tests CI, et sur postgresql+psycopg://... ou mysql+pymysql://... en production.
              

              

                Stratégie 3 — Gestion du Pool de Connexions & des Verrous
                SQLite : Fichier local unique, activer PRAGMA journal_mode = WAL; et ouvrir/fermer une connexion courte par requête.
PostgreSQL / MySQL : Connexions TCP coûteuses à établir → utiliser obligatoirement un Pool de Connexions (QueuePool, psycopg_pool, PgBouncer).		
                Systématiquement dès qu'une API dépasse un seul serveur (cluster de plusieurs machines derrière Nginx où un fichier SQLite local ne peut plus être partagé sur le réseau).
