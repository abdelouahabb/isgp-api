Addendum I — Cryptographie Appliquée & Aide-Mémoire openssl (Hachage, HMAC, Chiffrement AES/RSA & Certificats TLS)

          Cryptographie & Sécurité
        


        

          
Comprendre sans confusion : Encodage vs Hachage vs Signature HMAC vs Chiffrement

          

            En sécurité des APIs et administration système Linux, confondre ces cinq opérations conduit à des failles critiques. Voici la matrice de décision exacte à conserver en permanence :
          

          

            

              
                

                  Opération
                  Est-ce Réversible ?
                  Utilise une Clé Secrète ?
                  Objectif Exact
                  Outils Standards (OpenSSL / Python)
                  Cas d'Usage en API Web
                

              
              
                

                  1. Encodage
(Base64, Hex, UTF-8)		
                  Oui, par tout le monde (0 sécurité)
                  Non
                  Transporter des octets binaires dans un canal texte (HTTP/JSON)
                  base64, openssl base64, base64.b64encode()
                  En-tête Authorization: Basic, segments d'un jeton JWT
                

                

                  2. Hachage Rapide
(SHA-256, SHA-512)		
                  Non (Irréversible)
                  Non
                  Garantir l'intégrité d'un fichier ou calculer l'empreinte d'une clé haute entropie
                  openssl dgst -sha256, sha256sum, hashlib.sha256()
                  Vérifier qu'une archive n'est pas altérée, stocker l'empreinte d'une API Key
                

                

                  3. Hachage Lent Salé (KDF)
(Scrypt, PBKDF2, Argon2)		
                  Non (Irréversible + Lent)
                  Non (Sel aléatoire public inclus)
                  Protéger les mots de passe humains contre le cassage par GPU
                  openssl passwd -6, generate_password_hash()
                  Colonne password_hash de la table users en base SQL
                

                

                  4. Signature HMAC
(HMAC-SHA256)		
                  Non (Vérifié par recalcul)
                  Oui (Clé secrète partagée)
                  Prouver à la fois l'intégrité ET l'authenticité de l'émetteur
                  openssl dgst -sha256 -hmac, hmac.new()
                  Signature des jetons Bearer/JWT (HS256) et des Webhooks (X-Webhook-Signature)
                

                

                  5. Chiffrement Symétrique
(AES-256-CBC / GCM)		
                  Oui (Avec la même clé secrète)
                  Oui (1 clé secrète unique pour chiffrer et déchiffrer)
                  Rendre un fichier ou une colonne illisible aux tiers tout en pouvant le restaurer
                  openssl enc -aes-256-cbc -pbkdf2, cryptography.fernet
                  Chiffrer une sauvegarde SQLite (.db.enc), un fichier .env ou un secret bancaire
                

                

                  6. Chiffrement Asymétrique
(RSA-4096, Ed25519)		
                  Oui / Vérifiable (Paire Privée / Publique)
                  Oui (Clé Privée secrète + Clé Publique distribuée)
                  Signer avec la clé privée et permettre à tous de vérifier avec la clé publique
                  openssl genpkey, openssl pkey, ssh-keygen
                  Certificats HTTPS/TLS, clés SSH, jetons JWT inter-microservices (RS256 / EdDSA)
                

              
            

          

        


        

          
Arbre de Décision Cryptographique : Quelle Opération Choisir en Architecture d'API ?

          
flowchart TD
    Goal["Quel est votre besoin de sécurité sur la donnée ?"]
    Goal -->|"Transporter des octets en texte ASCII\n(0 confidentialité)"| Enc["1. Encodage\nBase64 / Hex / URL-Encoding"]
    Goal -->|"Vérifier l'intégrité d'un fichier\n(Irréversible, sans clé)"| Hash["2. Hachage Rapide\nSHA-256 / SHA-512"]
    Goal -->|"Stocker un mot de passe utilisateur\nen base SQL (Irréversible + Lent)"| KDF["3. Hachage KDF Salé\nArgon2id / PBKDF2 / scrypt"]

    Goal -->|"Cacher un secret ou une sauvegarde\npour pouvoir le déchiffrer plus tard"| Cipher["5. Chiffrement Réversible\nAES-256-GCM/CBC (Symétrique) ou TLS 1.3"]

        


        
Les 14 Commandes openssl Indispensables en Terminal Linux

        

          

            
              

                Besoin Opérationnel
                Commande Exacte à Exécuter sous Linux
                Explication Technique & Précautions
              

            
            
              

                1. Générer un cookie_secret
(256 bits en Hexadécimal)		
                openssl rand -hex 32
                Produit 64 caractères hexadécimaux (32 octets d'entropie pure) parfaits pour TORNADO_COOKIE_SECRET.
              

              

                2. Générer une clé aléatoire
(Format Base64)		
                openssl rand -base64 32
                Produit une chaîne aléatoire compacte idéale pour une clé d'API (X-API-Key) ou un mot de passe BDD.
              

              

                3. Hacher un texte en SHA-256
(Sans saut de ligne \n)		
                printf '%s' "mon_texte" | openssl dgst -sha256
                Toujours utiliser printf '%s' (et non echo qui ajoute un \n invisible modifiant le hash !).
              

              

                4. Hacher un fichier en SHA-256
(Contrôle d'intégrité)		
                openssl dgst -sha256 ecole_isgp.db
                Calcule l'empreinte SHA-256 d'un fichier SQLite ou d'une archive (équivalent à sha256sum).
              

              

                5. Signer en HMAC-SHA256
(Test de Webhook / JWT)		
                printf '%s' '{"id":1}' | openssl dgst -sha256 -hmac "cle_secrete"
                Calcule exactement la signature attendue dans l'en-tête X-Webhook-Signature de votre API Tornado.
              

              

                6. Encoder / Décoder en Base64
                printf '%s' "admin:pass" | openssl base64 -A
echo "YWRtaW46cGFzcw==" | openssl base64 -d		
                L'option -A garde la sortie sur une seule ligne ; -d décode le Base64 vers le texte d'origine.
              

              

                7. Chiffrer un fichier en AES-256
(Sauvegarde sécurisée)		
                openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 -in base.db -out base.db.enc
                Chiffre base.db avec AES-256, un sel aléatoire et 600 000 itérations PBKDF2 (demande un mot de passe).
              

              

                8. Déchiffrer un fichier AES-256
                openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in base.db.enc -out base.db
                L'option -d (*decrypt*) restaure le fichier original à l'octet près à partir du mot de passe.
              

              

                9. Générer une clé privée RSA 4096
                openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out private.pem
                Crée une clé privée asymétrique RSA de 4096 bits. Toujours protéger par chmod 600 private.pem.
              

              

                10. Extraire la clé publique RSA
                openssl pkey -in private.pem -pubout -out public.pem
                Extrait la clé publique public.pem qui peut être partagée sans risque avec tous les microservices.
              

              

                11. Générer une clé Ed25519
(Courbe elliptique moderne)		
                openssl genpkey -algorithm Ed25519 -out ed_priv.pem && openssl pkey -in ed_priv.pem -pubout -out ed_pub.pem
                Algorithme asymétrique moderne : clés ultra-courtes, signatures ultra-rapides et sécurité maximale.
              

              

                12. Créer un certificat HTTPS/TLS
(Auto-signé 365 jours)		
                openssl req -x509 -newkey rsa:4096 -nodes -keyout key.pem -out cert.pem -days 365 -subj "/CN=localhost"
                Génère key.pem et cert.pem pour tester HTTPS en local (ex: Nginx ou Gunicorn --certfile).
              

              

                13. Inspecter un certificat .pem
                openssl x509 -in cert.pem -noout -subject -issuer -dates -fingerprint -sha256
                Affiche le propriétaire (subject), l'autorité émettrice (issuer) et les dates d'expiration du certificat.
              

              

                14. Tester le TLS d'une API distante
                openssl s_client -connect api.domaine.dz:443 -servername api.domaine.dz </dev/null
                Se connecte en TLS au port 443 pour diagnostiquer la chaîne de certificats et la version TLS (TLS 1.2 / 1.3).
              

            
          

        

      


      
      

        

          
Addendum II — Commandes Linux, Réseau, Diagnostic & Exploitation Serveur pour APIs en Production

          Administration Linux & DevOps
        


        

          Lorsqu'une API est déployée sur un serveur Linux (Ubuntu, Debian, RHEL/Rocky), l'ingénieur backend utilise quotidiennement ces commandes pour diagnostiquer les ports, filtrer les réponses JSON, analyser les logs d'erreurs et sécuriser les processus :
        


        

          

            
              

                Catégorie & Action
                Commande Linux de Référence
                Utilité en Développement & Production d'API
              

            
            
              

                Réseau — Voir les ports ouverts
                sudo ss -tulpn | grep -E "8888|8001|80|443"
                Affiche tous les processus en écoute TCP/UDP avec leur numéro de processus (PID).
              

              

                Réseau — Identifier qui bloque un port
                lsof -i :8888  ou  fuser 8888/tcp
                Indispensable face à l'erreur OSError: [Errno 98] Address already in use au lancement de Tornado.
              

              

                Processus — Arrêter proprement
                kill -15 <PID>  (ou kill -9 <PID> si figé)
                -15 (SIGTERM) permet à IOLoop.current().stop() de terminer les requêtes en cours avant de s'éteindre.
              

              

                Réseau — Tester un port TCP
                nc -zv 127.0.0.1 8888
                Vérifie avec Netcat si le port TCP 8888 (ou 5432 pour PostgreSQL) est ouvert à travers le pare-feu.
              

              

                Réseau — Diagnostic DNS & IP
                dig +short api.domaine.dz  |  ip -br a
                Vérifie la résolution DNS d'un nom de domaine et liste les adresses IP des cartes réseau du serveur.
              

              

                Réseau — Capturer les paquets HTTP
                sudo tcpdump -i lo -A -s 0 'tcp port 8888'
                Capture et affiche en ASCII (-A) les trames TCP/HTTP brutes circulant sur le port 8888.
              

              

                JSON — Formater & Filtrer avec jq
                curl -s http://127.0.0.1:8888/api/sandbox/formations | jq '.data[] | {id, titre}'
                Extrait, colorise et transforme les réponses JSON directement dans un pipeline Bash.
              

              

                Logs — Surveillance temps réel
                tail -f access.log | grep --line-buffered -E " (401|403|429|500) "
                Affiche en direct uniquement les requêtes en échec ou bloquées par la sécurité.
              

              

                Logs — Top 10 des IP (Anti-DoS)
                awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10
                Compte le nombre de requêtes par adresse IP cliente dans les journaux Nginx/Apache pour repérer un abus.
              

              

                Sécurité — Verrouiller .env et clés
                chmod 600 .env private.pem
                Interdit la lecture du fichier de secrets à tout autre compte utilisateur de la machine Linux (-rw-------).
              

              

                Sécurité — Pare-feu Linux ufw
                sudo ufw allow 22/tcp && sudo ufw allow 443/tcp && sudo ufw enable
                Ferme tous les ports entrants du serveur sauf SSH (22) et HTTPS (443), rendant le port Gunicorn 8000 inaccessible de l'extérieur.
              

              

                Prod — Gérer le démon systemd
                sudo systemctl restart isgp-api && sudo journalctl -u isgp-api -f
                Redémarre les workers Gunicorn de production et affiche leurs journaux système en continu.
              

            
          

        

      


      
      

        

          
Addendum III — Référentiel des Types MIME (Content-Type / Accept) & Comment les Utiliser dans Tornado

          Types MIME & Négociation HTTP
        


        

          
Anatomie d'un Type MIME (type/sous-type; paramètre=valeur — RFC 6838 / IANA)

          

            Sur le réseau HTTP, le corps d'un message (Body) n'est qu'une suite d'octets. C'est le Type MIME (*Multipurpose Internet Mail Extensions*) qui indique au destinataire comment interpréter ces octets :
            
    
              
  • Content-Type (En-tête descriptif du corps envoyé) : Indique le format du corps actuel (ex: le client envoie Content-Type: application/json ou application/x-www-form-urlencoded dans son POST ; Tornado répond avec Content-Type: application/json; charset=UTF-8 via self.write(dict) ou text/html; charset=utf-8 via self.render(...)).
    • 
              
  • Accept (En-tête de négociation du client) : Le client indique à Tornado sous quel format il souhaite recevoir la réponse (ex: Accept: application/json pour un client mobile vs Accept: text/html pour un navigateur Web).
    • 
              
  • Content-Disposition (Comportement d'affichage vs téléchargement) : inline affiche le document (PDF, image) directement dans l'onglet du navigateur, tandis que attachment; filename="rapport.pdf" ouvre la boîte de dialogue de téléchargement.
    • 
              
  • X-Content-Type-Options: nosniff (Sécurité) : Interdit au navigateur de deviner le type d'un fichier par son contenu (*MIME Sniffing*), bloquant l'exécution de scripts malveillants déguisés en image ou en fichier texte.
    •

Matrice des 12 Types MIME Incontournables & Leur Manipulation dans Tornado

        

          

            
              

                Type MIME Officiel (IANA)
                Lecture Entrante dans Tornado (Requête Client → Serveur)
                Émission Sortante par Tornado (Réponse Serveur → Client)
                Cas d'Usage en Architecture Web & API
              

            
            
              

                1. application/json
(Standard API REST)		
                tornado.escape.json_decode(self.request.body)
                self.write(dictionnaire)
(Auto-sérialisation JSON native !)		
                Échange de données structurées entre API REST, applications mobiles, React/Vue et microservices.
              

              

                2. application/problem+json
(Standard RFC 7807)		
                tornado.escape.json_decode(self.request.body)
                self.set_header("Content-Type", "application/problem+json"); self.write(err)
                Format international normalisé pour les erreurs d'API (type, title, status, detail).
              

              

                3. application/x-www-form-urlencoded
(Formulaire HTML classique)		
                self.get_body_argument("champ")
self.get_body_arguments("choix")		
                Envoyé par <form method="POST"> ou curl -d "a=1&b=2"
                Soumission de formulaires Web HTML (sans fichier) et requêtes de jetons OAuth2 (grant_type=password).
              

              

                4. multipart/form-data
(Formulaire + Upload Fichier)		
                Texte : self.get_body_argument("...")
Fichier : self.request.files.get("doc")		
                Envoyé par <form enctype="multipart/form-data"> ou curl -F
                Téléversement de fichiers (PDF, images, Excel) accompagnés de champs de formulaire texte.
              

              

                5. text/html; charset=utf-8
(Page Web Tornado Template)		
                N/A (Généré côté serveur)
                self.render("page.html", ...)
                Pages Web rendues par le moteur tornado.template, portails documentaires (Swagger UI).
              

              

                6. text/plain; charset=utf-8
(Texte brut)		
                self.request.body.decode("utf-8")
                self.set_header("Content-Type", "text/plain; charset=utf-8"); self.write("OK")
                Journaux de logs (.log), collections .http, sondes de santé minimalistes (/ping).
              

              

                7. text/csv; charset=utf-8
(Tableur CSV)		
                csv.DictReader(io.StringIO(self.request.body.decode()))
                self.set_header("Content-Type", "text/csv"); self.write(csv_texte)
                Export et import de tableaux comptables, listes d'inscriptions ou rapports compatibles Excel.
              

              

                8. text/event-stream
(Flux temps réel SSE)		
                Connexion persistante ouverte par new EventSource("/api/flux")
                self.set_header("Content-Type", "text/event-stream"); await self.flush()
                Notifications serveur temps réel (Server-Sent Events), progression de tâches ou streaming IA sur l'IOLoop.
              

              

                9. application/xml
(et application/soap+xml)		
                ElementTree.fromstring(self.request.body)
                self.set_header("Content-Type", "application/xml"); self.write(xml_str)
                Services Web historiques SOAP / WSDL, virements bancaires SEPA ISO 20022, flux RSS.
              

              

                10. application/pdf
(Document PDF)		
                f = self.request.files["pdf"][0]["body"]
                self.set_header("Content-Type", "application/pdf"); self.write(octets_pdf)
                Génération et téléchargement de factures, attestations de stage et convocations officielles.
              

              

                11. image/png, image/jpeg, image/svg+xml
                img = self.request.files["photo"][0]
                self.set_header("Content-Type", "image/png"); self.write(octets_png)
                Affichage d'avatars, graphiques statistiques générés à la volée, badges ou QR codes 2FA.
              

              

                12. application/octet-stream
(Binaire générique)		
                octets = self.request.body (bytes)
                self.set_header("Content-Type", "application/octet-stream"); self.write(octets)
                Flux binaire brut (archives .zip, sauvegardes SQLite chiffrées .db.enc) forçant le téléchargement.
              

            
          

        


        
Modèles d'Implémentation Python / Tornado : Lire, Négocier et Renvoyer chaque Type MIME

        
import csv, io, os
import tornado.escape
import tornado.web


# 1. INSPECTION DU TYPE MIME ENTRANT (POST : JSON vs Formulaire HTML vs Multipart)
class IngestionUniverselleHandler(tornado.web.RequestHandler):
    def post(self):
        ct = self.request.headers.get("Content-Type", "").split(";")[0].strip().lower()

        if ct == "application/json":
            donnees = tornado.escape.json_decode(self.request.body or b"{}")
            self.set_status(201)
            self.write({"source": "JSON", "recu": donnees})
            return

        if ct == "application/x-www-form-urlencoded":
            donnees = {k: self.get_body_argument(k) for k in self.request.body_arguments}
            self.set_status(201)
            self.write({"source": "Formulaire HTML (get_body_argument)", "recu": donnees})
            return

        if ct == "multipart/form-data":
            champ_titre = self.get_body_argument("titre", default="")
            fichiers = self.request.files.get("document", [])
            f_info = fichiers[0] if fichiers else {}
            nom_sain = os.path.basename(f_info.get("filename", "")) if f_info else None
            self.set_status(201)
            self.write({
                "source": "Multipart (body_arguments + request.files)",
                "titre": champ_titre,
                "fichier_nom": nom_sain,
                "fichier_mimetype": f_info.get("content_type"),
            })
            return

        self.set_status(415)
        self.write({"erreur": f"Type MIME '{ct}' non supporté (415 Unsupported Media Type)"})


# 2. NÉGOCIATION DE CONTENU (Header 'Accept') : Répondre en JSON, HTML ou CSV sur le même Handler !
class ExportFormationsHandler(tornado.web.RequestHandler):
    def get(self):
        formations = [
            {"id": 1, "titre": "Architecture API REST Tornado", "duree_jours": 5, "salle": "Salle A"},
            {"id": 2, "titre": "Templates Tornado & Formulaires", "duree_jours": 3, "salle": "Salle B"},
        ]
        accept = self.request.headers.get("Accept", "application/json")

        if "text/csv" in accept:
            tampon = io.StringIO()
            ecrivain = csv.DictWriter(tampon, fieldnames=["id", "titre", "duree_jours", "salle"])
            ecrivain.writeheader()
            ecrivain.writerows(formations)
            self.set_header("Content-Type", "text/csv; charset=utf-8")
            self.set_header("Content-Disposition", 'attachment; filename="formations_isgp.csv"')
            self.write(tampon.getvalue())
            return

        if "text/html" in accept:
            self.render("formations.html", formations=formations)
            return

        # Par défaut : self.write(dict) sérialise en application/json
        self.write({"total": len(formations), "data": formations})

      


      
      

        

          

            
Addendum IV — Cycle de Vie d'une API : Pourquoi voit-on presque toujours /api/v1 et si rarement /api/v2 ?

            

              Loi de Postel (Tolerant Reader), Changements Rétrocompatibles vs Breaking Changes, Coexistence Multi-Versions par Tables de Routage URLSpec Tornado, En-têtes de Dépréciation IETF RFC 8594 (Deprecation & Sunset) et Enveloppe de Pagination
            

          

          Architecture & Cycle de Vie API
        


        
        

          

            Arbre de Décision Architecturale : Rester sur /api/v1 (Additive Change) vs Créer /api/v2 (Breaking Change) & Cycle RFC 8594
            Diagramme Vectoriel Mermaid
          

          
flowchart LR
    Change["Évolution demandée sur l'API"]
    Check{"Les clients v1 existants\n(Apps Mobiles, Partenaires)\nvont-ils planter ?"}
    StayV1["ÉVOLUTION RÉTROCOMPATIBLE (90% des cas)\n- Ajout d'un champ JSON optionnel\n- Ajout d'une nouvelle route (/api/v1/certificats)\n- Nouveau paramètre query optionnel (?lang=fr)\n-> ON RESTE SUR /api/v1 !"]
    CreateV2["RUPTURE DE CONTRAT (Breaking Change)\n- Champ renommé ('intitule' -> 'titre') ou supprimé\n- Type modifié ('duree': 5 -> {'valeur': 5, 'unite': 'jours'})\n- Nouveau champ obligatoire en POST\n-> CRÉATION DES HANDLERS /api/v2 !"]
    Coexist["Période de Coexistence (6 à 12 mois)\n/api/v1 (Headers Deprecation + Sunset RFC 8594)\n+ /api/v2 (Nouveau contrat) actifs en parallèle"]
    Gone["Extinction de /api/v1 après la date Sunset\n-> Renvoie HTTP 410 Gone"]
    Change --> Check
    Check -->|"Non (Loi de Postel)"| StayV1
    Check -->|"Oui (Rupture)"| CreateV2
    CreateV2 --> Coexist --> Gone

        


        

          

            
              1. Pourquoi /api/v1 dure souvent 5 à 10 ans sans jamais passer en v2 ?
            
            

              Dans les grandes APIs mondiales (OpenAI /v1/chat/completions, Stripe /v1/charges, Kubernetes /apis/apps/v1), on voit presque toujours v1 parce que 90 % de la vie d'une API se fait par ajouts rétrocompatibles (Additive / Non-Breaking Changes) :
            

            
    
              
  • Loi de Postel (Tolerant Reader Pattern) : Lorsqu'on ajoute un nouveau champ "certifiant": true dans le JSON de /api/v1/formations, une application mobile codée il y a 2 ans qui lit uniquement formation.intitule ignore simplement la nouvelle clé sans planter.
    • 
              
  • Pourquoi écrire /api/v1 dès le Jour 1 alors ? C'est une assurance-vie architecturale : si vous publiez /api/formations sans /v1 dans 50 000 téléphones et qu'un jour vous devez changer le type d'un champ, vous êtes bloqué. Avec /api/v1 présent dès l'origine, vous montez /api/v2 à côté sans casser /api/v1 !
    • 
            

          


          

            
              2. Quand faut-il obligatoirement créer /api/v2 et comment déprécier /api/v1 ?
            
            

              On ne crée /api/v2 que lorsqu'une modification casse le code des clients existants (Breaking Change) : changement de type (5 devient {"valeur": 5, "unite": "jours"}), renommage/suppression de clé, ou nouveau champ requis en POST.
            

            
    
              
  • Coexistence par Tables de Routage URLSpec Tornado : Les deux ensembles de handlers get_v1_routes() et get_v2_routes() tournent simultanément dans la même tornado.web.Application.
    • 
              
  • En-têtes HTTP de Dépréciation (Norme IETF RFC 8594) : Tant que v1 est en sursis, le serveur injecte via self.set_header(...) : Deprecation: true, Sunset: Thu, 31 Dec 2026 23:59:59 GMT et Link: </api/v2/formations>; rel="successor-version".
    • 
            

          

        


        

          

            
              

                Nature du Changement
                Exemples Concrets en JSON / HTTP
                Impact sur les Clients v1
                Décision Architecturale
              

            
            
              

                Ajout Rétrocompatible
(Non-Breaking / Additive)		
                
                  • Ajouter une clé JSON en sortie ("niveau": "Avancé")

                  • Créer une nouvelle route GET /api/v1/certificats

                  • Ajouter un filtre optionnel ?salle=Alger
                		
                Aucun impact : les clients existants ignorent les clés/routes qu'ils n'utilisent pas.
                Rester sur /api/v1 (Ne jamais créer une v2 pour un simple ajout !)
              

              

                Rupture de Contrat
(Breaking Change)		
                
                  • Renommer "intitule" en "titre"

                  • Changer "duree": 5 (int) en "duree": {"valeur": 5, "unite": "jours"}

                  • Rendre un nouveau champ obligatoire dans POST
                		
                Crash immédiat (KeyError, TypeError ou rejet 422 sur les apps mobiles en production).
                Créer un module de routes /api/v2 et maintenir /api/v1 avec en-têtes Deprecation + Sunset.
              

              

                Piège de la Racine JSON
(Liste brute vs Enveloppe)		
                
                  • Mauvais : Renvoyer une liste brute [ {...}, {...} ]

                  • Bon : Renvoyer {"meta": {"total": 42, "page": 1}, "data": [...]}
                		
                Si la racine est une liste [...], impossible d'ajouter total ou next_cursor sans casser la racine !
                Toujours utiliser une enveloppe objet {"meta": ..., "data": [...]} dès /api/v1 (et requis par self.write(dict) de Tornado !).
              

              

                Les 4 Stratégies de Versioning
(Où placer le numéro ?)		
                
                  1. URI Path : /api/v1/formations (80 % des APIs)

                  2. Header Date : X-API-Version: 2026-11-01 (Stripe)

                  3. MIME Accept : Accept: application/vnd.isgp.v2+json

                  4. Query Param : ?version=2
                		
                Le versioning dans l'URI (/api/v1/) est le plus lisible dans curl, Swagger UI et les blocs location de Nginx.
                Utiliser /api/v1/ dans l'URL pour les versions majeures, et un en-tête pour les sous-versions mineures.

Architecture de Production : Reverse Proxy Nginx, Répartition de Charge (Load Balancing) & Haute Disponibilité Tornado

          

            En production, on n'expose jamais un processus Python unique directement sur Internet. Nginx est placé en frontal (Port 80/443) pour remplir deux missions critiques :
            1) Servir directement les fichiers statiques (/static/) via le noyau Linux (sendfile) sans solliciter Python, et
            2) Répartir les requêtes dynamiques (/api/... et Templates Tornado) entre 4 instances Tornado HTTPServer(xheaders=True) (ports 8001 à 8004) avec tolérance aux pannes automatique (Zero-Downtime Failover).

                Algorithme Nginx (upstream)
                Directive dans nginx.conf
                Principe d'Aiguillage & Cas d'Usage
              

            
            
              

                1. Round-Robin (Tourniquet)
                (Par défaut, aucune directive)
                Distribue les requêtes séquentiellement dans l'ordre exact : :8001 → :8002 → :8003 → :8004 → :8001. Idéal lorsque toutes les requêtes ont un temps d'exécution similaire.
              

              

                2. Least Connections
                least_conn;
                Envoie chaque nouvelle requête à l'instance ayant actuellement le moins de connexions actives. Recommandé pour les APIs REST où certaines requêtes SQL sont plus longues que d'autres.
              

              

                3. IP Hash (Affinité client)
                ip_hash;
                Calcule un hachage de l'adresse IP du client pour qu'un même utilisateur atterrisse toujours sur la même instance (utile uniquement si l'application stocke un état en mémoire locale).
              

              

                4. Weighted (Pondéré)
                server 127.0.0.1:8001 weight=3;
                Attribue 3 fois plus de requêtes à l'instance :8001 qu'aux autres (utile lors d'un déploiement progressif Canary ou sur des serveurs de puissances différentes).
