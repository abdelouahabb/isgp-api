Comprendre sans confusion : Encodage vs Hachage vs Signature HMAC vs Chiffrement

          

            En sécurité des APIs et administration système Linux, confondre ces cinq opérations conduit à des failles critiques. Voici la matrice de décision exacte à conserver en permanence :
          

          

            

              
                

                  Opération
                  Est-ce Réversible ?
                  Utilise une Clé Secrète ?
                  Objectif Exact
                  Outils Standards (OpenSSL / Python)
                  Cas d'Usage en API Web
                

              
              
                

                  1. Encodage
(Base64, Hex, UTF-8)		
                  Oui, par tout le monde (0 sécurité)
                  Non
                  Transporter des octets binaires dans un canal texte (HTTP/JSON)
                  base64, openssl base64, base64.b64encode()
                  En-tête Authorization: Basic, segments d'un jeton JWT
                

                

                  2. Hachage Rapide
(SHA-256, SHA-512)		
                  Non (Irréversible)
                  Non
                  Garantir l'intégrité d'un fichier ou calculer l'empreinte d'une clé haute entropie
                  openssl dgst -sha256, sha256sum, hashlib.sha256()
                  Vérifier qu'une archive n'est pas altérée, stocker l'empreinte d'une API Key
                

                

                  3. Hachage Lent Salé (KDF)
(Scrypt, PBKDF2, Argon2)		
                  Non (Irréversible + Lent)
                  Non (Sel aléatoire public inclus)
                  Protéger les mots de passe humains contre le cassage par GPU
                  openssl passwd -6, generate_password_hash()
                  Colonne password_hash de la table users en base SQL
                

                

                  4. Signature HMAC
(HMAC-SHA256)		
                  Non (Vérifié par recalcul)
                  Oui (Clé secrète partagée)
                  Prouver à la fois l'intégrité ET l'authenticité de l'émetteur
                  openssl dgst -sha256 -hmac, hmac.new()
                  Signature des jetons Bearer/JWT (HS256) et des Webhooks (X-Webhook-Signature)
                

                

                  5. Chiffrement Symétrique
(AES-256-CBC / GCM)		
                  Oui (Avec la même clé secrète)
                  Oui (1 clé secrète unique pour chiffrer et déchiffrer)
                  Rendre un fichier ou une colonne illisible aux tiers tout en pouvant le restaurer
                  openssl enc -aes-256-cbc -pbkdf2, cryptography.fernet
                  Chiffrer une sauvegarde SQLite (.db.enc), un fichier .env ou un secret bancaire
                

                

                  6. Chiffrement Asymétrique
(RSA-4096, Ed25519)		
                  Oui / Vérifiable (Paire Privée / Publique)
                  Oui (Clé Privée secrète + Clé Publique distribuée)
                  Signer avec la clé privée et permettre à tous de vérifier avec la clé publique
                  openssl genpkey, openssl pkey, ssh-keygen
                  Certificats HTTPS/TLS, clés SSH, jetons JWT inter-microservices (RS256 / EdDSA)

Les 14 Commandes openssl Indispensables en Terminal Linux

        

          

            
              

                Besoin Opérationnel
                Commande Exacte à Exécuter sous Linux
                Explication Technique & Précautions
              

            
            
              

                1. Générer un cookie_secret
(256 bits en Hexadécimal)		
                openssl rand -hex 32
                Produit 64 caractères hexadécimaux (32 octets d'entropie pure) parfaits pour TORNADO_COOKIE_SECRET.
              

              

                2. Générer une clé aléatoire
(Format Base64)		
                openssl rand -base64 32
                Produit une chaîne aléatoire compacte idéale pour une clé d'API (X-API-Key) ou un mot de passe BDD.
              

              

                3. Hacher un texte en SHA-256
(Sans saut de ligne \n)		
                printf '%s' "mon_texte" | openssl dgst -sha256
                Toujours utiliser printf '%s' (et non echo qui ajoute un \n invisible modifiant le hash !).
              

              

                4. Hacher un fichier en SHA-256
(Contrôle d'intégrité)		
                openssl dgst -sha256 ecole_isgp.db
                Calcule l'empreinte SHA-256 d'un fichier SQLite ou d'une archive (équivalent à sha256sum).
              

              

                5. Signer en HMAC-SHA256
(Test de Webhook / JWT)		
                printf '%s' '{"id":1}' | openssl dgst -sha256 -hmac "cle_secrete"
                Calcule exactement la signature attendue dans l'en-tête X-Webhook-Signature de votre API Tornado.
              

              

                6. Encoder / Décoder en Base64
                printf '%s' "admin:pass" | openssl base64 -A
echo "YWRtaW46cGFzcw==" | openssl base64 -d		
                L'option -A garde la sortie sur une seule ligne ; -d décode le Base64 vers le texte d'origine.
              

              

                7. Chiffrer un fichier en AES-256
(Sauvegarde sécurisée)		
                openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 -in base.db -out base.db.enc
                Chiffre base.db avec AES-256, un sel aléatoire et 600 000 itérations PBKDF2 (demande un mot de passe).
              

              

                8. Déchiffrer un fichier AES-256
                openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in base.db.enc -out base.db
                L'option -d (*decrypt*) restaure le fichier original à l'octet près à partir du mot de passe.
              

              

                9. Générer une clé privée RSA 4096
                openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out private.pem
                Crée une clé privée asymétrique RSA de 4096 bits. Toujours protéger par chmod 600 private.pem.
              

              

                10. Extraire la clé publique RSA
                openssl pkey -in private.pem -pubout -out public.pem
                Extrait la clé publique public.pem qui peut être partagée sans risque avec tous les microservices.
              

              

                11. Générer une clé Ed25519
(Courbe elliptique moderne)		
                openssl genpkey -algorithm Ed25519 -out ed_priv.pem && openssl pkey -in ed_priv.pem -pubout -out ed_pub.pem
                Algorithme asymétrique moderne : clés ultra-courtes, signatures ultra-rapides et sécurité maximale.
              

              

                12. Créer un certificat HTTPS/TLS
(Auto-signé 365 jours)		
                openssl req -x509 -newkey rsa:4096 -nodes -keyout key.pem -out cert.pem -days 365 -subj "/CN=localhost"
                Génère key.pem et cert.pem pour tester HTTPS en local (ex: Nginx ou Gunicorn --certfile).
              

              

                13. Inspecter un certificat .pem
                openssl x509 -in cert.pem -noout -subject -issuer -dates -fingerprint -sha256
                Affiche le propriétaire (subject), l'autorité émettrice (issuer) et les dates d'expiration du certificat.
              

              

                14. Tester le TLS d'une API distante
                openssl s_client -connect api.domaine.dz:443 -servername api.domaine.dz </dev/null
                Se connecte en TLS au port 443 pour diagnostiquer la chaîne de certificats et la version TLS (TLS 1.2 / 1.3).

          Lorsqu'une API est déployée sur un serveur Linux (Ubuntu, Debian, RHEL/Rocky), l'ingénieur backend utilise quotidiennement ces commandes pour diagnostiquer les ports, filtrer les réponses JSON, analyser les logs d'erreurs et sécuriser les processus :
        


        

          

            
              

                Catégorie & Action
                Commande Linux de Référence
                Utilité en Développement & Production d'API
              

            
            
              

                Réseau — Voir les ports ouverts
                sudo ss -tulpn | grep -E "8888|8001|80|443"
                Affiche tous les processus en écoute TCP/UDP avec leur numéro de processus (PID).
              

              

                Réseau — Identifier qui bloque un port
                lsof -i :8888  ou  fuser 8888/tcp
                Indispensable face à l'erreur OSError: [Errno 98] Address already in use au lancement de Tornado.

                kill -15 <PID>  (ou kill -9 <PID> si figé)

                Réseau — Tester un port TCP
                nc -zv 127.0.0.1 8888
                Vérifie avec Netcat si le port TCP 8888 (ou 5432 pour PostgreSQL) est ouvert à travers le pare-feu.
              

              

                Réseau — Diagnostic DNS & IP
                dig +short api.domaine.dz  |  ip -br a
                Vérifie la résolution DNS d'un nom de domaine et liste les adresses IP des cartes réseau du serveur.
              

              

                Réseau — Capturer les paquets HTTP
                sudo tcpdump -i lo -A -s 0 'tcp port 8888'
                Capture et affiche en ASCII (-A) les trames TCP/HTTP brutes circulant sur le port 8888.
              

              

                JSON — Formater & Filtrer avec jq
                curl -s http://127.0.0.1:8888/api/sandbox/formations | jq '.data[] | {id, titre}'
                Extrait, colorise et transforme les réponses JSON directement dans un pipeline Bash.
              

              

                Logs — Surveillance temps réel
                tail -f access.log | grep --line-buffered -E " (401|403|429|500) "
                Affiche en direct uniquement les requêtes en échec ou bloquées par la sécurité.
              

              

                Logs — Top 10 des IP (Anti-DoS)
                awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -n 10
                Compte le nombre de requêtes par adresse IP cliente dans les journaux Nginx/Apache pour repérer un abus.
              

              

                Sécurité — Verrouiller .env et clés
                chmod 600 .env private.pem
                Interdit la lecture du fichier de secrets à tout autre compte utilisateur de la machine Linux (-rw-------).
              

              

                Sécurité — Pare-feu Linux ufw
                sudo ufw allow 22/tcp && sudo ufw allow 443/tcp && sudo ufw enable
                Ferme tous les ports entrants du serveur sauf SSH (22) et HTTPS (443), rendant le port Gunicorn 8000 inaccessible de l'extérieur.

                sudo systemctl restart isgp-api && sudo journalctl -u isgp-api -f
                Redémarre les workers Gunicorn de production et affiche leurs journaux système en continu.
              

            
          

        

      


      
      

        

          
Addendum III — Référentiel des Types MIME (Content-Type / Accept) & Comment les Utiliser dans Tornado

          Types MIME & Négociation HTTP
        


        

          
Anatomie d'un Type MIME (type/sous-type; paramètre=valeur — RFC 6838 / IANA)

          

            Sur le réseau HTTP, le corps d'un message (Body) n'est qu'une suite d'octets. C'est le Type MIME (*Multipurpose Internet Mail Extensions*) qui indique au destinataire comment interpréter ces octets :
            
    
              
  • Content-Type (En-tête descriptif du corps envoyé) : Indique le format du corps actuel (ex: le client envoie Content-Type: application/json ou application/x-www-form-urlencoded dans son POST ; Tornado répond avec Content-Type: application/json; charset=UTF-8 via self.write(dict) ou text/html; charset=utf-8 via self.render(...)).
    • 
              
  • Accept (En-tête de négociation du client) : Le client indique à Tornado sous quel format il souhaite recevoir la réponse (ex: Accept: application/json pour un client mobile vs Accept: text/html pour un navigateur Web).
    • 
              
  • Content-Disposition (Comportement d'affichage vs téléchargement) : inline affiche le document (PDF, image) directement dans l'onglet du navigateur, tandis que attachment; filename="rapport.pdf" ouvre la boîte de dialogue de téléchargement.
    • 
              
  • X-Content-Type-Options: nosniff (Sécurité) : Interdit au navigateur de deviner le type d'un fichier par son contenu (*MIME Sniffing*), bloquant l'exécution de scripts malveillants déguisés en image ou en fichier texte.
    •

import csv, io, os
import tornado.escape
import tornado.web


# 1. INSPECTION DU TYPE MIME ENTRANT (POST : JSON vs Formulaire HTML vs Multipart)
class IngestionUniverselleHandler(tornado.web.RequestHandler):
    def post(self):
        ct = self.request.headers.get("Content-Type", "").split(";")[0].strip().lower()

        if ct == "application/json":
            donnees = tornado.escape.json_decode(self.request.body or b"{}")
            self.set_status(201)
            self.write({"source": "JSON", "recu": donnees})
            return

        if ct == "application/x-www-form-urlencoded":
            donnees = {k: self.get_body_argument(k) for k in self.request.body_arguments}
            self.set_status(201)
            self.write({"source": "Formulaire HTML (get_body_argument)", "recu": donnees})
            return

        if ct == "multipart/form-data":
            champ_titre = self.get_body_argument("titre", default="")
            fichiers = self.request.files.get("document", [])
            f_info = fichiers[0] if fichiers else {}
            nom_sain = os.path.basename(f_info.get("filename", "")) if f_info else None
            self.set_status(201)
            self.write({
                "source": "Multipart (body_arguments + request.files)",
                "titre": champ_titre,
                "fichier_nom": nom_sain,
                "fichier_mimetype": f_info.get("content_type"),
            })
            return

        self.set_status(415)
        self.write({"erreur": f"Type MIME '{ct}' non supporté (415 Unsupported Media Type)"})


# 2. NÉGOCIATION DE CONTENU (Header 'Accept') : Répondre en JSON, HTML ou CSV sur le même Handler !
class ExportFormationsHandler(tornado.web.RequestHandler):
    def get(self):
        formations = [
            {"id": 1, "titre": "Architecture API REST Tornado", "duree_jours": 5, "salle": "Salle A"},
            {"id": 2, "titre": "Templates Tornado & Formulaires", "duree_jours": 3, "salle": "Salle B"},

              1. Pourquoi /api/v1 dure souvent 5 à 10 ans sans jamais passer en v2 ?
            
            

              Dans les grandes APIs mondiales (OpenAI /v1/chat/completions, Stripe /v1/charges, Kubernetes /apis/apps/v1), on voit presque toujours v1 parce que 90 % de la vie d'une API se fait par ajouts rétrocompatibles (Additive / Non-Breaking Changes) :
            

            
    
              
  • Loi de Postel (Tolerant Reader Pattern) : Lorsqu'on ajoute un nouveau champ "certifiant": true dans le JSON de /api/v1/formations, une application mobile codée il y a 2 ans qui lit uniquement formation.intitule ignore simplement la nouvelle clé sans planter.
    • 
              
  • Pourquoi écrire /api/v1 dès le Jour 1 alors ? C'est une assurance-vie architecturale : si vous publiez /api/formations sans /v1 dans 50 000 téléphones et qu'un jour vous devez changer le type d'un champ, vous êtes bloqué. Avec /api/v1 présent dès l'origine, vous montez /api/v2 à côté sans casser /api/v1 !
    • 
            

          


          

            
              2. Quand faut-il obligatoirement créer /api/v2 et comment déprécier /api/v1 ?
            
            

              On ne crée /api/v2 que lorsqu'une modification casse le code des clients existants (Breaking Change) : changement de type (5 devient {"valeur": 5, "unite": "jours"}), renommage/suppression de clé, ou nouveau champ requis en POST.
            

            
    
              
  • Coexistence par Tables de Routage URLSpec Tornado : Les deux ensembles de handlers get_v1_routes() et get_v2_routes() tournent simultanément dans la même tornado.web.Application.
    • 
              
  • En-têtes HTTP de Dépréciation (Norme IETF RFC 8594) : Tant que v1 est en sursis, le serveur injecte via self.set_header(...) : Deprecation: true, Sunset: Thu, 31 Dec 2026 23:59:59 GMT et Link: </api/v2/formations>; rel="successor-version".
    •

                Ajout Rétrocompatible
(Non-Breaking / Additive)		
                
                  • Ajouter une clé JSON en sortie ("niveau": "Avancé")

                  • Créer une nouvelle route GET /api/v1/certificats

                  • Ajouter un filtre optionnel ?salle=Alger
                		
                Aucun impact : les clients existants ignorent les clés/routes qu'ils n'utilisent pas.
                Rester sur /api/v1 (Ne jamais créer une v2 pour un simple ajout !)
              

              

                Rupture de Contrat
(Breaking Change)		
                
                  • Renommer "intitule" en "titre"

                  • Changer "duree": 5 (int) en "duree": {"valeur": 5, "unite": "jours"}

                  • Rendre un nouveau champ obligatoire dans POST
                		
                Crash immédiat (KeyError, TypeError ou rejet 422 sur les apps mobiles en production).
                Créer un module de routes /api/v2 et maintenir /api/v1 avec en-têtes Deprecation + Sunset.
              

              

                Piège de la Racine JSON
(Liste brute vs Enveloppe)		
                
                  • Mauvais : Renvoyer une liste brute [ {...}, {...} ]

                  • Bon : Renvoyer {"meta": {"total": 42, "page": 1}, "data": [...]}
                		
                Si la racine est une liste [...], impossible d'ajouter total ou next_cursor sans casser la racine !
                Toujours utiliser une enveloppe objet {"meta": ..., "data": [...]} dès /api/v1 (et requis par self.write(dict) de Tornado !).

(Où placer le numéro ?)		
                
                  1. URI Path : /api/v1/formations (80 % des APIs)

                  2. Header Date : X-API-Version: 2026-11-01 (Stripe)

                  3. MIME Accept : Accept: application/vnd.isgp.v2+json

                  4. Query Param : ?version=2
                		
                Le versioning dans l'URI (/api/v1/) est le plus lisible dans curl, Swagger UI et les blocs location de Nginx.
                Utiliser /api/v1/ dans l'URL pour les versions majeures, et un en-tête pour les sous-versions mineures.

          Nginx File Offload & X-Accel
        


        

          Synergie chirurgicale Nginx + Tornado (@stream_request_body vs Offload Disque) : Attention au piège classique ! Chapitre 1 — Architecture & Cycle de Vie d'une Connexion SQLite3 dans Tornado (run_in_executor + Pragmas de Production)

          Zéro Serveur Externe • Standard Library sqlite3
        

        

          Dans Tornado, le serveur repose sur une boucle d'événements mono-thread (IOLoop). Comme la bibliothèque standard sqlite3 effectue des entrées/sorties disque synchrones, une requête SQL lourde ou un verrou disque exécuté directement sur le thread principal figerait toutes les autres connexions de l'IOLoop. La bonne pratique d'ingénierie sous Tornado consiste à encapsuler la transaction SQLite dans une fonction synchrone appelée via await tornado.ioloop.IOLoop.current().run_in_executor(None, fn) :
        


        

          

            
Cycle d'Exécution d'une Requête SQLite Paramétrée

            
sequenceDiagram
    participant C as Client HTTP
    participant IO as Boucle IOLoop Tornado (Mono-Thread Non-Bloquant)
    participant TP as ThreadPoolExecutor (run_in_executor)
    participant S as Moteur C SQLite3 (Fichier .db + .db-wal)
    C->>IO: 1. Requête HTTP (async def get / post dans RequestHandler)
    IO->>TP: 2. await IOLoop.current().run_in_executor(None, _requete_sqlite)
    Note over IO: L'IOLoop reste 100% libre pour servir les autres clients !
    TP->>S: 3. sqlite3.connect() + PRAGMA journal_mode=WAL
    TP->>S: 4. with closing(conn.cursor()) as cur -> sqlite3_prepare_v2 + COMMIT
    S-->>TP: 5. fetchone() / fetchall() -> dict(row) + conn.close() dans finally
    TP-->>IO: 6. Résolution du Future asynchrone
    IO-->>C: 7. self.write(json) (HTTP 200 / 201)

          

          

            

              Patron d'implémentation recommandé (TORNADO) :
              
            

            
from contextlib import closing
import sqlite3
import tornado.ioloop
import tornado.web

DB_PATH = "isgp_catalogue.db"

def ouvrir_connexion_sqlite() -> sqlite3.Connection:
    conn = sqlite3.connect(DB_PATH, timeout=5.0, check_same_thread=False)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode = WAL;")   # Lectures et écritures concurrentes
    conn.execute("PRAGMA synchronous = NORMAL;") # Optimal avec WAL
    conn.execute("PRAGMA foreign_keys = ON;")    # Clés étrangères activées
    conn.execute("PRAGMA busy_timeout = 5000;")  # Attente max 5000 ms sur verrou
    return conn

class FormationsHandler(tornado.web.RequestHandler):
    async def get(self):
        salle = self.get_query_argument("salle", default="Salle A")
        def _select_sync():
            conn = ouvrir_connexion_sqlite()
            try:
                with closing(conn.cursor()) as cur:
                    cur.execute("SELECT * FROM formations WHERE salle = ?", (salle,))
                    return [dict(r) for r in cur.fetchall()]
            finally:
                conn.close()
        data = await tornado.ioloop.IOLoop.current().run_in_executor(None, _select_sync)
        self.write({"data": data})

          

        


        
    
          
  • 1. Protection de l'IOLoop via run_in_executor : En déléguant l'appel sqlite3 au ThreadPoolExecutor standard via await IOLoop.current().run_in_executor(None, ...), la boucle d'événements Tornado continue d'accepter les requêtes HTTP concurrentes pendant l'accès disque.
    • 

  • 2. Connexion courte fermée dans finally : Contrairement à un serveur TCP distant, l'ouverture d'un descripteur sur un fichier SQLite local prend moins de 0.05 ms. Ouvrir et fermer proprement dans try / finally à chaque tâche garantit zéro conflit entre threads.
    • 

  • 3. Mode PRAGMA journal_mode = WAL + busy_timeout = 5000 : Permet aux threads du ThreadPoolExecutor d'exécuter des SELECT en parallèle pendant qu'un INSERT ou UPDATE est en cours.
    • 

  • 4. Activation obligatoire de PRAGMA foreign_keys = ON : SQLite désactive les clés étrangères par défaut sur chaque nouvelle connexion ; il faut toujours l'activer dans ouvrir_connexion_sqlite().
    •

Chapitre 3 — Transactions ACID, isolation_level, Mode autocommit (Python 3.12+) & Verrous BEGIN IMMEDIATE

          Contrôle Transactionnel
        


        

          La gestion des transactions dans le module standard sqlite3 possède une particularité historique essentielle à connaître pour éviter deux pièges classiques en production : les écritures non sauvegardées (oubli de commit) et les erreurs sqlite3.OperationalError: database is locked lors de montées de verrous concurrentes.
        


        

          

            
              

                Mode Transactionnel sqlite3
                Configuration à l'ouverture
                Comportement Exact & Cas d'Usage
              

            
            
              

                1. Mode Historique par Défaut
(LEGACY_TRANSACTION_CONTROL)		
                sqlite3.connect("app.db")
(isolation_level = "" par défaut)		
                
                  Python analyse vos chaînes SQL et émet implicitement un BEGIN uniquement avant une instruction DML (INSERT, UPDATE, DELETE, REPLACE). Si vous n'appelez pas conn.commit() (ou n'utilisez pas le bloc with conn:) avant conn.close(), toutes vos modifications sont annulées silencieusement (ROLLBACK) !
                
              

              

                2. Mode Autocommit Natif SQLite
(Chaque requête s'engage seule)		
                
                  Python 3.12+ : sqlite3.connect("app.db", autocommit=True)

                  Python ≤ 3.11 : sqlite3.connect("app.db", isolation_level=None)
                		
                
                  Désactive les transactions implicites de Python : le moteur C SQLite fonctionne dans son mode natif où chaque instruction individuelle est validée immédiatement sur disque, sauf si vous démarrez explicitement un bloc cur.execute("BEGIN IMMEDIATE") ... cur.execute("COMMIT"). Très apprécié dans les frameworks asynchrones et pour piloter manuellement les verrous.
                
              

              

                3. Mode PEP 249 Strict (Python 3.12+)
(Transaction toujours ouverte)		
                sqlite3.connect("app.db", autocommit=False)
                
                  Conforme à 100% à la norme PEP 249 (comme psycopg sur PostgreSQL) : une transaction est toujours active dès la première requête (même un SELECT), et vous validez par conn.commit() ou annulez par conn.rollback().
                
              

            
          

        


        

          

            

              Attention : que fait réellement with conn: sur un objet sqlite3.Connection ?
            

            

              Contrairement à un fichier (with open(...)), utiliser with conn: sur une connexion SQLite NE FERME PAS la connexion ! Il agit uniquement comme un gestionnaire de transaction :
            

            
conn = sqlite3.connect("app.db")
try:
    with conn:
        # Si tout réussit ici -> conn.commit() est appelé automatiquement
        # Si une exception survient -> conn.rollback() est appelé automatiquement !
        conn.execute("INSERT INTO formations (titre) VALUES (?)", ("API REST",))
finally:
    conn.close()  # La fermeture du fichier .db doit toujours être appelée explicitement !

          


          

            

              Astuce Senior : Pourquoi utiliser BEGIN IMMEDIATE pour les transactions Lecture-puis-Écriture ?
            

            

              Par défaut, une transaction SQLite démarre en mode DEFERRED (elle ne prend qu'un verrou de lecture au premier SELECT). Si deux requêtes HTTP lisent le solde d'un compte en même temps puis tentent toutes deux un UPDATE, la seconde échoue immédiatement avec SQLITE_BUSY sans même attendre le busy_timeout ! En démarrant par BEGIN IMMEDIATE, SQLite réserve le droit d'écriture dès le début en respectant le busy_timeout :
            

            
conn = sqlite3.connect("app.db", isolation_level=None, timeout=5.0)
conn.execute("BEGIN IMMEDIATE")  # Réserve le verrou d'écriture proprement (attend jusqu'à 5s)
try:
    places = conn.execute("SELECT places_restantes FROM sessions WHERE id = ?", (1,)).fetchone()[0]
    if places > 0:
        conn.execute("UPDATE sessions SET places_restantes = places_restantes - 1 WHERE id = ?", (1,))
    conn.execute("COMMIT")
except Exception:
    conn.execute("ROLLBACK")
    raise

          

        

      


      
      

        

          
Chapitre 4 — Cycle de Vie du Cursor vs Connection : Faut-il fermer le Curseur (cur.close()) ? Est-ce une bonne ou mauvaise habitude ?

          Hygiène des Ressources & C-API
        


        

          C'est l'une des questions les plus fréquentes en revue de code Python : « Puisque sqlite3 permet d'écrire directement conn.execute(...) et que je ferme la connexion à la fin de la requête HTTP, dois-je quand même créer et fermer mes curseurs avec cur.close() ? »
        


        

          

            

              Verdict Ingénieur : Fermer explicitement le curseur est une EXCELLENTE habitude (4 raisons techniques)
            

            
    
              
  1. 
                Libération déterministe du verrou C (sqlite3_finalize) : Sous le capot, chaque sqlite3.Cursor maintient une machine virtuelle C compilée (sqlite3_stmt*). Si vous exécutez un SELECT et ne lisez que la 1re ligne (fetchone()) sans fermer le curseur, l'instruction reste dans l'état active statement et garde un verrou de lecture jusqu'au passage du Garbage Collector.
              
    2. 
              
  2. 
                Indépendance vis-à-vis du Garbage Collector : En CPython, le comptage de références libère souvent le curseur rapidement, mais dès qu'une trace d'exception (traceback) capture les variables locales ou que le code tourne sous PyPy, le curseur reste ouvert en mémoire si cur.close() n'est pas appelé.
              
    3. 
              
  3. 
                Portabilité directe vers PostgreSQL (psycopg) et MySQL (PyMySQL) : La méthode raccourcie conn.execute() de sqlite3 est une extension non-standard (absente de psycopg2 et PyMySQL). Sur PostgreSQL/MySQL avec un Pool de connexions, la connexion n'est jamais fermée entre deux requêtes HTTP : seul le curseur est fermé !
              
    4. 
              
  4. 
                Clarté du périmètre d'exécution : Délimiter la durée de vie du curseur indique exactement à quel moment la lecture des résultats SQL est terminée.
              
    5. 
            

          


          

            

              Attention au piège syntaxique en sqlite3 : Utilisez contextlib.closing(conn.cursor()) !
            

            

              Contrairement à psycopg (PostgreSQL) ou PyMySQL, l'objet sqlite3.Cursor de la bibliothèque standard n'implémente pas les méthodes __enter__ et __exit__ ! Écrire with conn.cursor() as cur: en sqlite3 lève une AttributeError: __enter__. Le patron canonique en Python consiste à utiliser from contextlib import closing :
            

            
from contextlib import closing

# MAUVAISE PRATIQUE (lève AttributeError en sqlite3 standard) :
# with conn.cursor() as cur:  --> AttributeError: __enter__ !

# BONNE PRATIQUE UNIVERSELLE (fonctionne en sqlite3, psycopg, PyMySQL) :
with closing(conn.cursor()) as cur:
    cur.execute("SELECT id, titre FROM formations WHERE salle = ?", ("Salle A",))
    row = cur.fetchone()
# Ici, cur.close() a été appelé automatiquement et déterministement,
# même si vous n'avez lu qu'une seule ligne sur 10 000 ou si une exception est levée !

              1. Pourquoi les développeurs Flask adorent l'ORM (SQLAlchemy) — et ce qu'il cache

  1. Vérifie d'abord son cache mémoire (Identity Map).
    2. 
              
  2. Emprunte une connexion, crée un cursor DB-API 2.0, lie (1,) et appelle fetchone().
    3. 
              
  3. Ferme immédiatement le curseur et retourne une instance de classe Python.
    4. 
            

            
# Style ORM idiomatique sous Flask (SQLAlchemy 2.0) :
@app.get("/api/formations/<int:id>")
def get_formation(id: int):
    # Aucun curseur visible : db.session gère le curseur C
    stmt = db.select(Formation).where(Formation.id == id)
    obj = db.session.execute(stmt).scalar_one_or_none()
    if obj is None:
        return jsonify({"erreur": "Introuvable"}), 404

@app.get("/api/formations/{id}")

Chapitre 6 — sqlite3 (Bibliothèque Standard) vs APSW (Another Python SQLite Wrapper) vs aiosqlite : Quelle Différence ?

          Comparatif des Pilotes SQLite
        


        

          Lorsqu'un architecte Python conçoit un service appuyé sur SQLite, deux grandes bibliothèques C s'affrontent : le module intégré sqlite3 (dérivé de pysqlite) et APSW (Another Python SQLite Wrapper). Bien qu'elles parlent toutes deux au même moteur C SQLite, leur philosophie est radicalement opposée :
        


        

          

            
              

                Critère Technique
                sqlite3 (Standard Library Python)
                apsw (Another Python SQLite Wrapper)
                aiosqlite (Asyncio Bridge)
              

            
            
              

                Philosophie & Norme
                Implémente la norme PEP 249 (DB-API 2.0) pour offrir la même interface générique que PostgreSQL ou MySQL.
                Ne suit volontairement PAS la PEP 249 ! Expose 100% de l'API C native de SQLite (sqlite3.h) sans couche d'abstraction trompeuse.
                Enveloppe le module standard sqlite3 dans un thread d'arrière-plan piloté par des coroutines async / await.
              

              

                Installation
                Inclus d'office dans Python (zéro dépendance externe).
                Paquet C externe (pip install apsw), compilé avec la toute dernière version officielle d'amalgamation SQLite.
                Paquet externe pur Python (pip install aiosqlite).
              

              

                Gestion des Transactions
                Ouvre des transactions implicites (BEGIN caché avant INSERT/UPDATE) sauf si isolation_level=None ou autocommit=True.
                100% fidèle à SQLite C : aucune transaction cachée. Vous utilisez with connection: (qui gère même les transactions imbriquées via SAVEPOINT !) ou vos propres BEGIN IMMEDIATE.
                Hérite du comportement de sqlite3 (nécessite await db.commit()).
              

              

                Exécution de plusieurs requêtes dans un seul execute()
                Interdit : cur.execute("SELECT 1; SELECT 2;") lève ProgrammingError: You can only execute one statement at a time (et executescript() refuse les paramètres ?).
                Supporté nativement avec paramètres liés : cursor.execute("INSERT INTO a VALUES (?); SELECT * FROM a WHERE x = ?;", (10, 10)) compile et exécute chaque instruction à la suite en toute sécurité !
                Identique à sqlite3 (1 seule instruction par execute).
              

              

                Fonctionnalités Avancées SQLite C
                Sous-ensemble limité (fonctions scalaires, agrégats simples, sauvegarde backup()).
                Couverture intégrale : Tables Virtuelles (Virtual Tables), systèmes de fichiers virtuels (VFS en RAM ou chiffrés), flux Blob incrémental (zeroblob), hooks wal_hook, cache automatique de requêtes préparées, ExecutionTrace.
                Sous-ensemble de sqlite3.
              

              

                Quand le choisir ?
                Choix par défaut (95% des projets) : APIs Web, laboratoires sans installation, compatibilité SQLAlchemy et portabilité vers PostgreSQL/MySQL.
                Usage intensif / embarqué critique : Lorsque SQLite est votre base définitive de production et que vous voulez toute la puissance de l'API C SQLite sans les compromis de la PEP 249.
                Routes async def sous FastAPI ou Tornado si vous ne souhaitez pas utiliser de ThreadPool.
              

            
          

        


        

          

            

              Exemple avec sqlite3 (Standard PEP 249) :
            

            
import sqlite3

conn = sqlite3.connect("catalogue.db")
# 1. Une seule instruction autorisée par execute()
# 2. Nécessite commit() ou with conn:
with conn:
    cur = conn.execute("INSERT INTO formations (titre) VALUES (?)", ("API REST",))
    for row in conn.execute("SELECT id, titre FROM formations WHERE id = ?", (cur.lastrowid,)):
        print(row)

Chapitre 8 — Sécurité SQL & Portabilité : Pourquoi ? dans SQLite vs %s dans PostgreSQL / MySQL (Norme PEP 249 / DB-API 2.0)

          Architecture & Sécurité Multi-SGBD
        


        

          En Python, tous les pilotes relationnels (sqlite3, psycopg pour PostgreSQL, PyMySQL / mysql-connector pour MySQL, oracledb, pyodbc) respectent la spécification officielle PEP 249 (Python Database API Specification v2.0). Le principe fondamental de sécurité est identique partout : séparer la compilation syntaxique de la requête (le code SQL) de la transmission des données (les paramètres). En revanche, la syntaxe du marqueur de paramètre (paramstyle) change selon le moteur de base de données :
        


        

          

            
              

                Moteur SGBD & Pilote Python
                Style PEP 249 (paramstyle)
                Syntaxe Positionnelle (Tuple en 2e argument)
                Syntaxe Nommée (Dictionnaire en 2e argument)
              

            
            
              

                SQLite 3
sqlite3 (Inclus dans Python, utilisé dans ce laboratoire)		
                qmark (?) &
named (:nom)		
                
                  cur.execute("SELECT * FROM formations WHERE salle = ? AND duree_jours >= ?", (salle, min_j))

                  Piège d'1 seul paramètre : écrire (id,) avec une virgule finale, jamais (id) !
                		
                
                  cur.execute("SELECT * FROM formations WHERE salle = :salle AND duree_jours >= :min_j", {"salle": salle, "min_j": min_j})

                  Idéal dès que la requête comporte plus de 3 paramètres.
                		
              

              

                PostgreSQL
psycopg2 / psycopg 3		
                format (%s) &
pyformat (%(nom)s)

                  Utilise %s quel que soit le type (int, str, date, bool).
                		
                
                  cur.execute("SELECT * FROM formations WHERE salle = %(salle)s", {"salle": salle})
                
              

              

                MySQL / MariaDB
PyMySQL / mysql-connector		
                format (%s) &
pyformat (%(nom)s)

                Oracle Database
oracledb

                Microsoft SQL Server
pyodbc

              Piège Critique sur PostgreSQL / MySQL : Ne JAMAIS confondre la virgule , et l'opérateur Python % !
            

            

              Sur MySQL et PostgreSQL, le marqueur s'écrit %s. De nombreux développeurs débutants commettent l'erreur mortelle d'utiliser l'opérateur de formatage Python % au lieu de passer un second argument à execute() :
            

            
# VULNÉRABILITÉ CRITIQUE D'INJECTION SQL (Opérateur % de Python) :
cur.execute("SELECT * FROM users WHERE email = '%s'" % email)  # INTERDIT !

# SÉCURISÉ (Virgule : le tuple est passé en 2e argument au pilote) :
cur.execute("SELECT * FROM users WHERE email = %s", (email,))  # CORRECT (PostgreSQL/MySQL)
cur.execute("SELECT * FROM users WHERE email = ?", (email,))   # CORRECT (SQLite)

          


          

            

              Ce que ni ? ni %s ne peuvent paramétrer : Les Identifiants SQL (ORDER BY, Colonnes, Tables)
            

            

              Un marqueur de requête préparée (? ou %s) ne peut lier qu'une valeur littérale. Si vous écrivez ORDER BY ?, SQLite trie sur une constante texte et non sur la colonne ! Pour dynamiser un tri ou un nom de colonne, utilisez obligatoirement une Liste Blanche (Allowlist) :
            

            
# Liste blanche stricte côté serveur (valable sur SQLite, PostgreSQL et MySQL) :
COLONNES_AUTORISEES = {"id": "id", "duree": "duree_jours", "titre": "titre"}
colonne_sure = COLONNES_AUTORISEES.get(param_utilisateur, "id")
direction_sure = "DESC" if ordre_utilisateur == "desc" else "ASC"

# Seuls les identifiants validés par dictionnaire sont interpolés ; les valeurs restent en `?` :
sql = f"SELECT * FROM formations WHERE salle = ? ORDER BY {colonne_sure} {direction_sure}"
cur.execute(sql, (salle,))

Chapitre 2 — Implémentation dans Tornado (IOLoop Non-Bloquante C10K) & Le Défi C10K (10 000 Connexions Ouvertes)

          SSE, WebSocket & C10K
        


        

          Comportement de Tornado (IOLoop Non-Bloquante C10K) face aux connexions longues :

          Tornado a été littéralement conçu à l'origine (FriendFeed, 2009) pour résoudre le problème C10K (maintenir plus de 10 000 connexions temps réel ouvertes simultanément sur un seul processus Python via epoll / kqueue). C'est également la raison pour laquelle Jupyter Notebook / JupyterLab utilise tornado.websocket.WebSocketHandler pour relier votre navigateur aux noyaux d'exécution Python en direct ! Avec await self.flush() et StreamClosedError, Tornado offre un contrôle chirurgical sur le flux TCP.
        


        

          Piège de production n°1 derrière un Reverse Proxy Nginx : Par défaut, Nginx accumule les réponses de votre serveur Python dans un tampon mémoire de 4 Ko ou 8 Ko avant de les expédier au navigateur. Résultat : vos petits événements SSE restent bloqués chez Nginx et arrivent tous d'un seul bloc à la fin ! Pour obtenir un véritable streaming instantané, renvoyez toujours l'en-tête X-Accel-Buffering: no (ou configurez proxy_buffering off; sur la route SSE dans nginx.conf).

class SseTelemetryHandler(tornado.web.RequestHandler):

                await self.flush()

Chapitre 3 — Téléversement de Fichiers : Pourquoi multipart/form-data écrase le Base64-dans-JSON

            

              Calcul d'inflation binaire (+33 %), saturation du parseur JSON et anatomie exacte d'une trame RFC 7578
            

          

          Partie II — Fichiers & Binaire
        


        

          Une erreur fréquente chez les développeurs débutants consiste à convertir un fichier PDF ou une photo en texte Base64 côté navigateur pour l'insérer dans un champ JSON : {"titre": "Support", "fichier_b64": "JVBERi0xLjcK..."}. Dès que les fichiers dépassent quelques centaines de kilo-octets, cette approche provoque deux dégradations sévères en production :
        


        

          

            
              

                Critère d'Ingénierie
                Anti-Pattern : Base64 dans application/json
                Standard Production : multipart/form-data (RFC 7578)
              

            
            
              

                Taille sur le réseau
                +33 % d'inflation mathématique (3 octets binaires sont codés sur 4 caractères ASCII) : un fichier de 60 Mo pèse 80 Mo sur la 4G !

import hashlib, os, uuid
import tornado.web

PLAFOND_OCTETS = 5 * 1024 * 1024  # 5 Mo maximum
DOSSIER_QUARANTAINE = "/tmp/isgp_uploads_securises"
os.makedirs(DOSSIER_QUARANTAINE, exist_ok=True)

# EXCLUSIVITÉ TORNADO : @stream_request_body désactive la mise en mémoire tampon complète
# de self.request.body et livre les paquets réseau bruts à data_received(chunk) au fil de l'eau !
@tornado.web.stream_request_body
class StreamUploadHandler(tornado.web.RequestHandler):
    def prepare(self):
        # Barrière #1 : Rejet immédiat dès l'en-tête Content-Length si > 5 Mo
        self.request.connection.set_max_body_size(PLAFOND_OCTETS)
        self.octets_recus = 0
        self.entete_binaire = bytearray()
        self.empreinte = hashlib.sha256()
        self.chemin_temp = os.path.join(DOSSIER_QUARANTAINE, f"{uuid.uuid4().hex}.upload")
        self._fichier = open(self.chemin_temp, "wb")

    def data_received(self, chunk: bytes):
        # Appelé à chaque paquet TCP reçu : empreinte mémoire RAM proche de ZÉRO !
        if len(self.entete_binaire) < 16:
            self.entete_binaire.extend(chunk[: 16 - len(self.entete_binaire)])
        self.octets_recus += len(chunk)
        self.empreinte.update(chunk)
        self._fichier.write(chunk)

    def post(self):
        self._fichier.close()
        # Barrière #2 : Inspection des Magic Bytes sur le flux reçu (%PDF-)
        if b"%PDF-" not in bytes(self.entete_binaire):
            os.remove(self.chemin_temp)
            self.set_status(415)
            return self.write({"status": 415, "erreur": "Signature binaire %PDF- introuvable"})

        self.set_status(201)
        self.write({
            "fichier_stocke": os.path.basename(self.chemin_temp),
            "octets_stream": self.octets_recus,
            "sha256": self.empreinte.hexdigest(),
        })

Chapitre 5 — Tâches Lourdes & Files d'Arrière-Plan : Le Patron HTTP 202 Accepted + Location

            

              Pourquoi une route HTTP ne doit jamais durer plus de 500 ms, et comment éviter la panne en cascade 504 Gateway Timeout
            

          

          Partie III — Asynchrone & Observabilité
        


        

          Imaginez qu'un responsable pédagogique clique sur « Générer les 300 attestations PDF signées de la promotion » (durée du calcul : 18 secondes). Si vous exécutez ce calcul à l'intérieur de la route POST avant de répondre :
          1) sous Gunicorn WSGI, le worker est gelé pendant 18 secondes (4 clics simultanés paralysent tout le serveur !) ;
          2) sur mobile ou derrière Cloudflare / Nginx, le proxy coupe brutalement la connexion en 504 Gateway Timeout pendant que le client ignore si l'opération a réussi ou échoué et reclique trois fois !
          La solution normalisée par l'IETF (RFC 9110 §15.3.3) est le code 202 Accepted :
        


        

          

            Découplage Asynchrone par Jeton de Tâche : POST -> 202 Accepted + Suivi d'Avancement Non-Bloquant
            Diagramme de Séquence Mermaid

    participant U as Client Web / Mobile
    participant A as API TORNADO (Worker HTTP)
    participant Q as Exécuteur d'Arrière-Plan / File Redis

          Règle d'architecture — Tâche locale en mémoire vs File distribuée (Celery / RQ / ARQ + Redis) :

          • En mémoire dans le processus API (ThreadPoolExecutor en Flask, BackgroundTasks en FastAPI, IOLoop.spawn_callback en Tornado) : parfait pour les tâches courtes (< 10 s) non critiques (envoi d'un e-mail de notification, purge d'un fichier temporaire, écriture d'audit). Si le conteneur Docker redémarre au milieu, la tâche en cours est perdue.

          • File persistante externe (Celery, RQ ou ARQ adossé à Redis / RabbitMQ ou table SQLite WAL dédiée) : obligatoire dès que la tâche est critique (facturation, paiement, génération lourde CPU/IA), car elle survit au redémarrage de l'API et offre des tentatives automatiques (*Retries* avec *Exponential Backoff*).

Chapitre 6 — Middlewares d'Observabilité : Corrélation X-Request-ID & Horloge Monotone perf_counter

            

              Relier instantanément le ticket d'erreur d'un utilisateur à la ligne exacte des journaux serveur et mesurer la latence au centième de milliseconde
            

          

          Traçabilité & Latence
        


        

          En production, lorsque 80 utilisateurs appellent votre API dans la même seconde et qu'un client vous signale : « J'ai reçu une erreur à 14h02 », des journaux texte ordinaires sont inexploitables. Deux règles d'ingénierie transforment le diagnostic :
          1) Corrélation X-Request-ID : dès l'entrée dans le middleware, si Nginx a déjà injecté un identifiant valide (vérifié par expression régulière stricte ^[a-zA-Z0-9_-]{6,64}$ pour empêcher toute attaque par Log Injection de faux retours à la ligne !), on le conserve ; sinon on génère req-<uuid>, on le passe aux tâches d'arrière-plan, on l'inclut dans les erreurs RFC 7807 et on le renvoie dans l'en-tête HTTP de réponse.
          2) Chronométrage par time.perf_counter() : n'utilisez jamais time.time() pour mesurer une durée d'exécution ! Si le démon réseau NTP recale l'horloge système de -50 ms au milieu d'une requête, time.time() peut afficher une durée négative ! time.perf_counter() utilise l'horloge matérielle monotone haute résolution du processeur.
        


        

          

            
              

                Framework
                Points d'Accroche du Cycle de Vie (Hooks)
                Stockage Isolé de l'ID de Requête
              

            
            
              

                Flask (WSGI)
                @app.before_request → vue → @app.after_request → @app.teardown_request
                Objet proxy contextuel flask.g.request_id (isolé par thread / contexte Werkzeug).
              

              

                FastAPI (ASGI)
                @app.middleware("http") enveloppant response = await call_next(request) (modèle en pelure d'oignon).
                request.state.request_id ou contextvars.ContextVar (isolé par tâche asyncio concurrente !).
              

              

                Tornado (IOLoop)
                prepare(self) → get()/post() → on_finish(self) sur une classe de base BaseHandler.
                Attribut d'instance self.request_id (Tornado instancie un nouveau RequestHandler par requête HTTP).
              

            
          

        


        
          Implémentation complète Middleware X-Request-ID + Tâche 202 Accepted (Tornado (IOLoop Non-Bloquante C10K)) :
        
        
import asyncio, json, re, time, uuid
import tornado.ioloop, tornado.web

REGEX_REQ_ID = re.compile(r"^[a-zA-Z0-9_-]{6,64}$")
REGISTRE_JOBS = {}

# --- CLASSE DE BASE OBSERVABLE : Cycle prepare() -> méthode HTTP -> on_finish() ---
class ObservableBaseHandler(tornado.web.RequestHandler):
    def prepare(self):
        self._t0 = time.perf_counter()
        id_entrant = self.request.headers.get("X-Request-ID", "")
        self.request_id = id_entrant if REGEX_REQ_ID.match(id_entrant) else f"req-{uuid.uuid4().hex[:12]}"
        self.set_header("X-Request-ID", self.request_id)

    def write_headers_timing(self):
        duree_ms = (time.perf_counter() - self._t0) * 1000.0
        self.set_header("X-Process-Time-Ms", f"{duree_ms:.2f}")

# --- TÂCHE DÉTACHÉE SUR L'IOLOOP : spawn_callback + HTTP 202 Accepted ---
class ExportCertificatsHandler(ObservableBaseHandler):
    async def _executer_job_arriere_plan(self, job_id: str):
        REGISTRE_JOBS[job_id]["statut"] = "RUNNING"
        await asyncio.sleep(3.0)  # Tâche asynchrone détachée de la requête HTTP !
        REGISTRE_JOBS[job_id].update({"statut": "COMPLETED", "url_telechargement": f"/exports/{job_id}.pdf"})

    async def post(self):
        job_id = f"job-{uuid.uuid4().hex[:8]}"
        REGISTRE_JOBS[job_id] = {"job_id": job_id, "statut": "PENDING", "request_id": self.request_id}

        # Détache la coroutine sur l'IOLoop : la requête HTTP répond 202 en < 1 ms !
        tornado.ioloop.IOLoop.current().spawn_callback(self._executer_job_arriere_plan, job_id)

        self.set_status(202)
        self.set_header("Location", f"/api/v1/jobs/{job_id}")
        self.set_header("Retry-After", "2")
        self.write_headers_timing()
        self.write(REGISTRE_JOBS[job_id])

      


      
      
      
      

        

          

            
Chapitre 7 — Cache HTTP Intelligent (RFC 9111) : Cache-Control, ETag & 304 Not Modified

            

              La requête la plus rapide et la plus écologique est celle dont on n'a pas besoin de transférer le corps JSON
            

          

          Partie IV — Cache & Concurrence
        


        

          Un catalogue de formations est lu 10 000 fois par jour mais modifié seulement 3 fois par semaine. Renvoyer à chaque fois 85 Ko de JSON gaspille la bande passante mobile et le CPU de sérialisation. À l'inverse, mettre en cache par erreur la réponse de GET /api/profil sur un proxy partagé exposerait les données personnelles d'un utilisateur au suivant ! Maîtriser les directives Cache-Control et l'empreinte ETag (Entity Tag, entourée de guillemets doubles selon la norme HTTP : ETag: "a91f4c...") est indispensable :
        


        

          

            
              

                En-tête / Directive HTTP
                Signification Exacte (Navigateur & CDN)
                Quand l'utiliser impérativement
              

            
            
              

                Cache-Control: no-store
                Interdiction absolue d'écrire la réponse sur disque ou en cache partagé.
                Obligatoire sur /auth/token, données bancaires, dossiers RH/personnels et jetons secrets.
              

              

                Cache-Control: private, no-cache
                Seul le navigateur de l'utilisateur peut conserver la copie, mais il doit revalider l'ETag auprès du serveur avant chaque usage.
                Données métier propres à un utilisateur connecté susceptibles de changer à tout instant.
              

              

                Cache-Control: public, max-age=60, must-revalidate
                Réponse réutilisable sans appel réseau pendant 60 s ; au-delà, revalidation légère via If-None-Match → 304 Not Modified (0 octet de Body !).
                Catalogues publics, nomenclatures, référentiels géographiques, listes de formations.
              

              

                ETag Fort ("8f3a19...")
vs ETag Faible (W/"v3")		
                Un ETag fort garantit une égalité à l'octet près (requis pour If-Match et téléchargements partiels) ; W/ indique une équivalence sémantique.
                Privilégiez toujours un ETag fort calculé par SHA-256 canonique ou numéro de version de ligne SQLite.
              

            
          

        

      


      
      
      
      

        

          

            
Chapitre 8 — Contrôle de Concurrence Optimiste : Éliminer le Bug du Lost Update avec If-Match & 412 Precondition Failed

            

              Comment empêcher deux administrateurs qui éditent la même fiche d'écraser silencieusement le travail l'un de l'autre
            

          

          If-Match & 412 Anti-Collision
        


        

          L'ETag ne sert pas qu'au cache de lecture (`GET`) : c'est aussi l'arme royale pour sécuriser les écritures concurrentes (`PUT` / `PATCH` / `DELETE`) !
          Scénario classique du Lost Update : À 10h00, Amine et Sarah ouvrent tous les deux la Formation #1 (ETag: "v1-a8f2", 40 places). À 10h01, Sarah change les places à 25 et sauvegarde (le serveur passe en ETag: "v2-91c0"). À 10h02, Amine — dont l'écran affiche toujours l'ancienne fiche de 10h00 — modifie uniquement la salle et envoie PUT avec places: 40. Sans protection, Amine écrase silencieusement la modification de Sarah !
          Avec l'en-tête If-Match: "v1-a8f2", le serveur compare l'ETag d'Amine avec l'ETag actuel ("v2-91c0"), détecte la collision et répond HTTP 412 Precondition Failed.
        


        
          Implémentation conjointe GET 304 + PUT If-Match 412 (Tornado (IOLoop Non-Bloquante C10K)) :
        
        
import hashlib, json
import tornado.web

def calculer_etag_fort(ressource: dict) -> str:
    canonique = json.dumps(ressource, sort_keys=True, ensure_ascii=False).encode("utf-8")
    return f'"{hashlib.sha256(canonique).hexdigest()[:16]}"'

class FormationCatalogueHandler(tornado.web.RequestHandler):
    # Note : Tornado possède aussi compute_etag() / check_etag_header() intégrés ;
    # l'écrire explicitement permet de maîtriser à la fois GET (304) et PUT If-Match (412) !
    def get(self, id_f: str):
        doc = charger_formation_sqlite(int(id_f))
        etag_actuel = calculer_etag_fort(doc)
        self.set_header("ETag", etag_actuel)
        self.set_header("Cache-Control", "private, max-age=30, must-revalidate")

        if self.request.headers.get("If-None-Match") == etag_actuel:
            self.set_status(304)
            return self.finish()  # Zéro octet de corps transféré !

        self.write(doc)

    def put(self, id_f: str):
        doc = charger_formation_sqlite(int(id_f))
        etag_actuel = calculer_etag_fort(doc)
        if_match = self.request.headers.get("If-Match")

        if not if_match:
            self.set_status(428)
            return self.write({"status": 428, "title": "En-tête If-Match obligatoire"})
        if if_match != etag_actuel:
            self.set_status(412)
            self.set_header("ETag", etag_actuel)
            return self.write({"status": 412, "title": "Conflit d'édition (Lost Update évité)"})

        doc_maj = appliquer_mise_a_jour_sqlite(int(id_f), json.loads(self.request.body))
        self.set_header("ETag", calculer_etag_fort(doc_maj))
        self.write(doc_maj)

Chapitre 1 — Qu'est-ce qu'une API réellement ? (Au-delà du Web : la Frontière d'Abstraction et de Découplage)

            

              Comprendre l'essence architecturale d'une Application Programming Interface avant de choisir un protocole ou un framework
            

          

          Partie I — Fondations & Terminologie
        


        

          Une API (Application Programming Interface — Interface de Programmation d'Application) n'est pas « un serveur JSON sur Internet » : au sens strict du génie logiciel, une API est une frontière formelle de découplage entre deux composants logiciels qui définit avec exactitude CE QUE le fournisseur accepte de faire (opérations, entrées, sorties, erreurs possibles), tout en dissimulant intégralement COMMENT il le réalise en interne (langage, algorithmes, moteur de base de données, topologie matérielle).
        


        

          Analogie de Référence — Le Poste de Conduite Normalisé : Lorsque vous montez dans une voiture thermique, hybride ou 100 % électrique, le volant, les pédales et le compteur constituent l'API publique du véhicule. Le constructeur peut remplacer un moteur essence par deux moteurs électriques et une batterie lithium-fer-phosphate (changement radical d'implémentation interne) : tant que le contrat des pédales et du volant ne change pas, aucun conducteur n'a besoin d'être rééduqué. En informatique, cette propriété permet à une application mobile iOS/Android de continuer à fonctionner sans mise à jour pendant que l'équipe Backend remplace un monolithe PHP par des microservices Python/Rust !

Chapitre 2 — Le Lexique Fondamental de l'Ingénieur API : 12 Termes Essentiels Définis avec Précision

            

              Ne plus jamais confondre Ressource et Représentation, Endpoint et Route, 400 et 422, Idempotence, SLI, SLO et SLA
            

          

          Vocabulaire de Précision
        


        

          En réunion d'architecture comme en diagnostic d'incident de production, l'ambiguïté de vocabulaire coûte très cher. Voici les 12 distinctions exactes qu'un concepteur d'API maîtrise sur le bout des doigts :
        


        

          

            
              

                Terme / Couple de Concepts
                Définition Exacte & Nuance Technique
                Illustration Concrète
              

            
            
              

                1. Ressource vs Représentation
                La Ressource est l'entité métier conceptuelle identifiée par son URI ; la Représentation est la projection sérialisée (JSON, XML, CSV, PDF) transmise sur le réseau à un instant donné.
                Ressource : /api/formations/42
Représentations : application/json ou text/csv de cette même formation n°42.		
              

              

                2. URI vs Endpoint vs Route
                L'URI identifie la ressource (/api/formations/42) ; l'Endpoint associe un verbe précis et une URL (DELETE /api/formations/42) ; la Route est la règle paramétrée côté code serveur qui capture l'appel.
                Endpoint : GET /api/formations/42
Route Python : /api/formations/<int:id> ou {id}.		
              

              

                3. Headers (En-têtes) vs Payload (Corps)
                Les Headers constituent l'enveloppe de contrôle lue par les proxys, passerelles et caches sans ouvrir le colis ; le Payload (Body) contient la donnée métier transportée.
                Headers : Authorization, Content-Type, ETag
Payload : {"titre": "Audit API", "duree_jours": 5}.		
              

              

                4. Idempotence & Idempotency-Key
                Une opération est idempotente si l'exécuter 1 fois ou 10 fois de suite laisse le serveur dans le même état. GET, PUT, DELETE le sont par norme ; POST ne l'est pas sauf ajout d'une clé d'idempotence UUID.
                POST /paiements + Idempotency-Key: 7f8c... → zéro double débit bancaire en cas de réessai mobile !
              

              

                5. Statelessness (Sans État Mémoire)
                Contrainte REST majeure : le serveur ne conserve aucun contexte client en RAM entre deux requêtes. Chaque requête transporte tout ce qu'il faut pour la traiter (ex: jeton signé).
                La requête 1 peut atterrir sur le worker :8001 et la requête 2 sur :8004 sans aucune perte de session.
              

              

                6. Désérialisation (400) vs Validation (422)
                La désérialisation transforme les octets UTF-8 en structure Python (échoue en 400 Bad Request si JSON tronqué) ; la validation vérifie le contrat métier (échoue en 422 Unprocessable Content).
                {"duree":  → 400 (syntaxe cassée)
{"duree": -5} → 422 (JSON valide mais règle métier violée).		
              

              

                7. Content Negotiation (406 vs 415)
                Mécanisme HTTP permettant au client et au serveur de s'accorder sur le format MIME à l'aller (Content-Type) et au retour (Accept).
                Envoi d'un XML non supporté → 415 Unsupported Media Type.
Demande Accept: application/pdf impossible → 406 Not Acceptable.		
              

              

                8. Pagination Offset vs Cursor (Keyset)
                ?limit=20&offset=100000 oblige la BDD à scanner et jeter 100 000 lignes ; la pagination par curseur (?after_id=98412&limit=20) saute instantanément via l'index B-Tree en O(log N).
                Sur 5 millions de transactions : OFFSET prend 900 ms ; WHERE id > :cursor LIMIT 20 prend 0,4 ms.
              

              

                9. Webhook (API Inversée)
                Au lieu que le client fasse du polling inutile, il enregistre une URL de rappel (Callback URL). Dès qu'un événement se produit, le serveur émet un POST signé cryptographiquement.
                En-tête X-ISGP-Signature-256: sha256=... vérifié avec hmac.compare_digest() avant traitement.
              

              

                10. SDK (Software Development Kit)
                Bibliothèque cliente typée (Python, TypeScript, Kotlin, Go) encapsulant les appels HTTP, les retries, l'authentification et les modèles d'une API — idéalement générée depuis OpenAPI.
                client.inscriptions.create(formation_id=3) au lieu d'assembler manuellement urllib/fetch.
              

              

                11. Rate-Limiting, Quota & Backpressure
                Le Rate-Limit plafonne le débit instantané (ex: 20 req/s) ; le Quota plafonne le volume mensuel (ex: 100 000 appels/mois) ; la Backpressure signale au client de ralentir.
                Réponse HTTP 429 Too Many Requests accompagnée de l'en-tête Retry-After: 30.
              

              

                12. SLI vs SLO vs SLA
                SLI = mesure réelle observée ; SLO = objectif interne d'ingénierie ; SLA = contrat commercial incluant des pénalités financières si l'engagement est rompu.
                SLI : latence p99 = 84 ms.
SLO interne : 99,95 %.
SLA client : remboursement sous 99,9 % (max 43 min d'arrêt/mois).		
              

            
          

        

      


      
      
      
      

        

          

            
Chapitre 3 — Contrat d'API vs Documentation d'API : Gouvernance, Cycle de Vie & Zéro Dérive

            

              Pourquoi un document Word ou un Wiki Confluence n'est PAS un contrat, et comment industrialiser l'évolution sans jamais casser vos clients
            

          

          Gouvernance & Contrats
        


        

          L'erreur la plus répandue dans les équipes débutantes consiste à confondre Contrat d'API et Documentation d'API. Lorsqu'un développeur écrit une page Wiki manuelle décrivant ses routes, puis modifie un champ Python trois semaines plus tard en urgence sans mettre à jour le Wiki, la documentation ment : c'est la dérive documentaire (Documentation Drift), source numéro 1 des bugs d'intégration Mobile/Backend.
        


        

          

            
Le Contrat d'API (Vérité Exécutable par Machine)

            

              Un contrat est une spécification mathématique déterministe lisible sans ambiguïté par un automate informatique (OpenAPI 3.1 adossé à JSON Schema, Protobuf .proto ou AsyncAPI). Il fige les types scalaires et composites, les bornes numériques, les expressions régulières, les attributs obligatoires (required) ainsi que l'intégralité des codes de statut HTTP possibles (200, 201, 401, 403, 422, 429) et l'enveloppe d'erreur normalisée RFC 9457 / 7807.
            

            

              Pouvoir industriel en CI/CD : loin d'être un texte passif, ce fichier pilote l'audit grammatical continu (Spectral), le blocage préventif des ruptures de compatibilité (oasdiff), l'émulation immédiate de serveurs de simulation (Prism Mock) et le test de robustesse par génération mathématique de charges limites (Schemathesis).
            

          


          

            
La Documentation d'API (Expérience Humaine — DX)

            

              Une documentation constitue le portail cognitif conçu pour l'ingénieur humain chargé d'intégrer votre service. Elle articule le récit opérationnel qu'aucun schéma brut ne saurait raconter seul : prise en main en cinq minutes (Quickstart), cinématique d'obtention et de renouvellement des jetons OAuth 2.0, bac à sable d'essai et enchaînement chronologique des appels métiers de bout en bout.
            

            

              Garantie zéro dérive : son catalogue technique interactif (Swagger UI, ReDoc ou Scalar) n'est jamais rédigé à la main, mais projeté automatiquement depuis le fichier openapi.yaml officiel à chaque déploiement.

L'architecture Zero-Trust (« Ne jamais faire confiance à l'IP, toujours vérifier cryptographiquement ») impose que chaque requête Est-Ouest prouve (1) quel microservice parle ET (2) quel utilisateur humain lui a délégué quel droit précis. C'est la raison d'être exacte d'OAuth 2.0.
        

      


      
      
      
      

        

          

            
Chapitre 5 — OAuth 2.0 (RFC 6749), OpenID Connect (OIDC) & PKCE (RFC 7636)

            

              Les 4 rôles canoniques, la différence vitale entre Authentification (ID Token) et Autorisation (Access Token), et les flux OAuth 2.1
            

          

          Délégation d'Autorisation
        


        

          Avant OAuth 2.0, lorsqu'une application tierce (ex: un outil de comptabilité ou une application mobile) voulait lire vos factures ou vos contacts, elle vous demandait votre identifiant et votre mot de passe principal. C'était une catastrophe de sécurité : l'application tierce obtenait 100 % de vos droits (y compris supprimer votre compte), stockait votre mot de passe sur ses propres serveurs, et le seul moyen de révoquer son accès était de changer votre mot de passe partout.
        


        

          L'Analogie Fondatrice — La Clé de Voiturier (Valet Key) : À l'hôtel, vous ne donnez jamais votre clé maîtresse permanente au voiturier : vous lui remettez une clé de voiturier qui autorise à démarrer le moteur et rouler à 30 km/h pendant 15 minutes (scope: drive:parking, exp: +900s), mais refuse mécaniquement d'ouvrir le coffre ou la boîte à gants. OAuth 2.0 est l'usine officielle de clés de voiturier numériques signées cryptographiquement.
        


        
1. Les 4 Rôles Canoniques d'OAuth 2.0 & la Frontière OAuth 2.0 vs OpenID Connect (OIDC)

        

          

            
              

                Acteur / Jeton
                Rôle Exact dans la Chaîne de Confiance
              

            
            
              

                1. Resource Owner
                L'entité (généralement l'utilisateur humain, ex: Amine Benali) propriétaire des données et seule habilitée à consentir à une délégation.
              

              

                2. Client (Application)
                L'application qui souhaite agir au nom de l'utilisateur : soit Client Public (PWA navigateur, app iOS/Android — incapable de garder un secret caché), soit Client Confidentiel (serveur Backend protégé).
              

              

                3. Authorization Server (IdP)
                Le serveur d'identité centralisé (Keycloak, Auth0, Okta, Microsoft Entra ID, Google Identity) : il authentifie l'utilisateur (mot de passe, Passkey/WebAuthn, MFA), vérifie son consentement et signe les jetons avec sa clé privée RSA/Ed25519.
              

              

                4. Resource Server (Votre API)
                Votre serveur Python (Tornado (IOLoop Non-Bloquant C10K)) qui héberge les ressources protégées (/api/v2/inscriptions). Il ne gère aucun mot de passe : il valide la signature du jeton via les clés publiques JWKS de l'IdP, puis contrôle exp, aud et scope.
              

              

                OIDC ID Token (Authentification = QUI)
                Ajouté par la surcouche OpenID Connect (OIDC). Destiné exclusivement au Client (aud == client_id) pour savoir qui vient de se connecter (nom, email, photo). Interdiction formelle d'envoyer un ID Token pour appeler une API !
              

              

                OAuth2 Access Token (Autorisation = QUOI)
                La clé de voiturier envoyée dans Authorization: Bearer <token> au Resource Server (aud == https://api.isgp.dz/service-inscriptions). Porte les permissions déléguées (scope: "formations:read inscriptions:write") et dure 5 à 15 minutes.

Chapitre 6 — Opérations Authentifiées Déléguées en Est-Ouest : Du Piège du Confused Deputy au Token Exchange (RFC 8693)

            

              Comment propager l'identité d'un utilisateur à travers 4 microservices internes sans jamais créer un « passe-partout » universel dangereux
            

          

          Zero-Trust & Laboratoire Live
        


        

          Suivons une opération réelle de bout en bout : Amine clique sur « S'inscrire et payer » dans l'application Web (flux Nord-Sud). Le Service-Inscriptions reçoit la requête, mais pour finaliser le dossier, il doit appeler en interne (flux Est-Ouest) le Service-Paiement pour débiter les frais de formation. Quel jeton le Service-Inscriptions doit-il présenter au Service-Paiement ?
        


        

          

            
L'Anti-Pattern Fatal : Blind Token Passthrough (Le Confused Deputy)

            

              Si vous émettez un jeton géant aud: "*" valable pour tout le SI et que chaque microservice transfère aveuglément l'en-tête Authorization: Bearer reçu au suivant : le jour où un microservice secondaire peu critique (ex: Service-Statistiques ou Service-Avatar) subit une faille, l'attaquant récupère les jetons des utilisateurs qui y passent et les rejoue directement contre le Service-Paiement ! Le Service-Paiement devient un Adjoint Confus (Confused Deputy) incapable de distinguer un appel légitime d'un rejeu latéral pirate.
            

          


          

            
L'Architecture Industrielle : Phantom Token + mTLS + RFC 8693

            

              1. Bordure (Phantom Token) : Sur Internet, le client ne détient qu'un jeton opaque illisible ; l'API Gateway le convertit en JWT ciblant uniquement aud: service-inscriptions.

              2. Transport Est-Ouest : Connexion mTLS prouvant cryptographiquement que la machine appelante est bien spiffe://.../service-inscriptions.

              3. OAuth 2.0 Token Exchange (RFC 8693) : Service-Inscriptions échange le jeton entrant auprès de l'IdP contre un jeton neuf de 120 secondes ciblant aud: service-paiement, un scope minimal paiement:debit_inscription et la claim act (Actor) !

Chapitre 7 — Qu'est-ce que Swagger ? (Histoire Complète & Distinction Exacte entre Swagger et OpenAPI 3.1)

            

              Lever définitivement la confusion la plus fréquente du monde des APIs : la Norme ouverte (OpenAPI) face aux Outils (Swagger)
            

          

          Partie III — OpenAPI & Écosystème Swagger
        


        

          Au quotidien, beaucoup de développeurs disent « Envoie-moi le fichier Swagger de ton API » ou « J'ai ouvert le Swagger ». Pourquoi deux noms coexistent-ils (Swagger et OpenAPI), et que désigne chacun avec exactitude ? Tout s'explique par un tournant historique majeur survenu en novembre 2015 :
        


        

          

            
              

                Période
                Jalon Historique
                Impact Technique pour les Architectes d'APIs
              

            
            
              

                2010 – 2014
                Création de Swagger 1.0 → 2.0
                Tony Tam (chez Wordnik, puis Reverb et SmartBear Software) crée un format JSON/YAML simple pour décrire ses APIs REST et générer simultanément une interface Web de test et des SDKs clients. Jusqu'à la version swagger: "2.0", le mot Swagger désigne à la fois le fichier de contrat ET les outils.
              

              

                Novembre 2015
                Don à la Linux Foundation (Naissance d'OpenAPI)
                Pour que le standard devienne neutre et universel (comme Linux ou Kubernetes), SmartBear fait don de la spécification à l'OpenAPI Initiative (OAI) sous l'égide de la Linux Foundation (Google, Microsoft, IBM, PayPal...). La spécification est renommée OpenAPI Specification (OAS), tandis que SmartBear conserve la marque commerciale Swagger pour sa suite d'outils !
              

              

                2017 – Aujourd'hui
                OpenAPI 3.0 puis OpenAPI 3.1
                openapi: 3.0.x restructure les composants réutilisables, le multi-serveurs et les flux OAuth 2.0. En 2021, openapi: 3.1.0 réalise l'alignement à 100 % avec JSON Schema Draft 2020-12 et supporte nativement la description des webhooks entrants/sortants.
              

            
          

        


        

          La Règle Mnémotechnique Définitive : La différence entre OpenAPI et Swagger est exactement la même qu'entre HTML5 (la norme standard ouverte du W3C) et Google Chrome / Firefox (les logiciels qui affichent une page HTML5) :

          • OpenAPI (OAS 3.1) = LA SPÉCIFICATION (Le Contrat) : le fichier standard openapi.yaml ou openapi.json gouverné par la Linux Foundation.

          • Swagger = LES OUTILS LOGICIELS (créés par SmartBear) qui exploitent un contrat OpenAPI :
          Swagger Editor (éditeur YAML/JSON avec validation temps réel), Swagger UI (le célèbre portail HTML/JS interactif avec le bouton « Try it out » et le cadenas OAuth2 « Authorize »), et Swagger Codegen (générateur de code serveur et de SDKs clients).

Chapitre 9 — Synthèse de Référence : Les 7 Piliers d'une Architecture API d'Entreprise Irréprochable

            

              Comment toutes les briques de ce cours s'assemblent dans un système de production réel
            

          

          

            
          

        


        

          

            
              

                #
                Couche Architecturale
                Décision d'Ingénierie de Production
              

            
            
              

                1
                Contrat & Documentation
                Un contrat formel OpenAPI 3.1 versionné et vérifié en CI (Spectral + Schemathesis) qui pilote automatiquement Swagger UI / ReDoc, les erreurs normalisées RFC 7807 et les en-têtes de cycle de vie RFC 8594 (Deprecation / Sunset).
              

              

                2
                Bordure Nord-Sud (Edge)
                Terminaison TLS 1.3 publique, bouclier de taille client_max_body_size (413), délestage binaire ($request_body_file / X-Accel-Redirect), Rate-Limiting (429) et conversion Phantom Token sur Nginx / API Gateway.
              

              

                3
                Authentification & Délégation Nord-Sud
                OpenID Connect (OIDC) pour identifier l'humain côté Client (ID Token) + OAuth 2.1 Authorization Code avec PKCE (RFC 7636) pour émettre un Access Token à vie courte et scope minimal.
              

              

                4
                Maillage Interne Est-Ouest
                Politique Zero-Trust : chiffrement et identité machine mutuelle par mTLS (SPIFFE) + OAuth 2.0 Token Exchange (RFC 8693) verrouillant l'audience (aud) et la chaîne d'acteurs (act) — ou client_credentials pour les démons autonomes.
              

              

                5
                Fiabilité Métier & Cache HTTP
                Clé Idempotency-Key sur les POST critiques (zéro double débit), cache conditionnel ETag / If-None-Match (304) et verrouillage optimiste If-Match (412).
              

              

                6
                Moteur Python & Persistance
                Choix éclairé du modèle d'exécution (Flask WSGI, FastAPI ASGI ou Tornado IOLoop), requêtes SQL 100 % paramétrées anti-SQLi, mode WAL sur SQLite embarqué ou pool de connexions PostgreSQL en cluster.
              

              

                7
                Observabilité & Gouvernance SRE
                Propagation bout-en-bout d'un identifiant de corrélation X-Request-ID / W3C traceparent à travers Nord-Sud et Est-Ouest, journaux JSON structurés et suivi continu des SLI / SLO / SLA.
